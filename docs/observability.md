# 可观测（M13）：为什么这里没有"CPU > 80% 就告警"

> 这份文档解释可观测模块的设计取舍。核心问题只有一个：
> **什么样的告警值得看？**
>
> 答案不是"越多越好"。一个天天响的告警等于没有告警。

---

## 一、先说结论：只报「组合异常」

`nxs metrics` 的输出里没有阈值告警。这是刻意的。

`docs/design/01-system-definition.md` 对 M13 的约束原文是：

> 告警要建在**系统级关联**上，不能只到单个节点。

这条约束容易被当成"再加一层聚合"，其实它说的是**判据形态**：

| 形态 | 例子 | 问题 |
|---|---|---|
| 单指标阈值 | "响应字节 > 1MB 告警" | 正常的汇总任务天天触发 |
| 单指标阈值 | "请求频率 > 100/s 告警" | 正常批量任务天天触发 |
| **组合判断** | "字节大 **且** 任务多" | 单看都正常，同时出现才可疑 |

阈值告警的根本问题：**它不知道上下文**。同一个数字在两种场景下含义相反。

所以本模块的每条规则都必须是"单看正常、合起来可疑"的形态。
这条要求用一个字段来强制落地 —— 见下。

---

## 二、`rationale` 字段：规则的资格证明

每条 :class:`Anomaly` 都有一个 ``rationale``，内容必须是
**"为什么单独看每个指标都不算异常"**：

```json
{
  "rule": "probe_pattern",
  "rationale": "有拒绝很正常（默认拒绝必然拒）。反复撞同一条规则通常只是
                配置写错，是良性的。但一个节点撞到多种互不相关的规则，
                更像在逐条试探边界——配错不会这么分散。"
}
```

写不出这句话的规则，说明它只是阈值告警，**不该放在这个模块里**。
有一条测试专门检查这点（``test_every_rule_has_rationale``）。

这不是文档洁癖：它把"这条规则凭什么存在"变成可执行的门槛。

---

## 三、五条规则，以及它们各自的反例

每条都配一个"单看正常时不该报"的反例。**反例才是这类规则的价值证明。**

### ① `bulk_movement` — 批量搬运

**判据**：某节点的应答字节与完成量**同时**远超同类（各 5 倍以上）。

| 单看 | 为什么正常 |
|---|---|
| 字节多 | 做汇总、出报告的节点本来就产得多 |
| 任务多 | 今天活多的节点就该多 |

**合起来**：形态接近批量导出数据。这时才值得看一眼。
（注意是"值得看一眼"，不是"断定攻击"。）

**反例**：只有字节大、任务不多 → **不报**。

### ② `probe_pattern` — 权限试探

**判据**：同一节点撞到 **3 种以上互不相关的拒绝规则**。

| 单看 | 为什么正常 |
|---|---|
| 有拒绝 | 本系统默认拒绝，没配好的调用必然被拒 |
| 某条规则命中多 | 几乎总是配置写错，修一下就好，是良性的 |

**合起来**：撞到多种互不相关的规则，说明在逐条敲墙。
配错的人只会反复撞同一堵墙。

**反例**：只撞同一条规则 20 次 → **不报**（那是配错，由 `denial_dominance` 报）。

### ③ `dead_route` — 给离线节点派活

**判据**：节点状态为 `stale` 或 `revoked`，但名下仍有待办或执行中任务。

| 单看 | 为什么正常 |
|---|---|
| 节点 stale | 下班关机完全正常 |
| 队列有待办 | 队列本来就该有待办 |

**合起来**：给已知离线的节点派活，那批任务只能等租约超时才回队列。
**不会报错，只会慢** —— 慢到让人以为系统坏了。

**反例**：离线但名下没活 → **不报**。

### ④ `silent_stall` — 静默卡死

**判据**：积压水位 ≥ 3 倍并发上限，**且**完成数与失败数都是 0。

| 单看 | 为什么正常 |
|---|---|
| 积压高 | 可能刚来一批任务 |
| 暂时没完成 | 任务正在算 |

**合起来**：有积压证明有活进来，零产出证明一个都没出去。
**不是慢，是不动。**

**反例**：积压高但有产出 → **不报**（那只是忙）。

> ⚠ **判据分两档，因为"零产出"有两种含义。**
>
> v0.8 初版用**累计**零产出判断，实测时发现一个真实漏报：
> **节点先正常工作一批、然后才卡死**。那时累计产出早已不为 0，
> 规则永远不响——而这才是最典型的卡死形态（一开始就零产出的节点
> 反而少见）。
>
> 所以有上一次快照时改用**增量**判断：
>
> | 情况 | 判据 |
> |---|---|
> | 有 `previous` | 两次采样之间产出为 0 **且**积压增长（准确） |
> | 无 `previous` | 自启动以来零产出（保守，会漏但不误报） |
>
> 生产环境里 `nxs metrics` 是反复调用的，所以走的都是准确的那条。

**反例**：两次采样间有产出 → **不报**（那只是慢）。

### ⑤ `denial_dominance` — 拒绝结构异常

**判据**：拒绝率 > 50%，**且**某一条规则吃掉 > 80% 的拒绝。

| 单看 | 为什么正常 |
|---|---|
| 拒绝率高 | 默认拒绝的系统里很正常 |
| 某规则命中多 | 正常 |

**合起来**：一条规则吃掉绝大部分拒绝，几乎总是**配置漏了**
（矩阵 allow_types 少写一个类型之类），是良性问题。

这和 `probe_pattern` 配合起来才有分辨力：

| 拒绝分布 | 结论 |
|---|---|
| 集中在一条规则 | 配错了 → `denial_dominance`（warn） |
| 分散在多条规则 | 在试探 → `probe_pattern`（critical） |

**反例**：拒绝率高但分散 → **不报**"配错"。

## 四、和审计（M12）的分工

这两个模块容易混，但它们回答完全不同的问题：

| | 审计 M12 | 可观测 M13 |
|---|---|---|
| 回答 | 三个月前谁给谁派过活 | 现在系统健康吗 |
| 形态 | append-only 落盘，可取证 | 内存计数，会丢 |
| 读取成本 | 扫文件 O(n) | 取快照 O(1) |
| 重启后 | 还在 | **归零** |

所以**指标不读审计日志**。审计是 NDJSON 追加文件，长期运行后
按 10 万行去算 p95，每次查询都要把整个文件读进内存。
把两种用途混在一起，会让"看一眼监控"变成一次磁盘扫描。

⚠ **进程重启后指标归零。** 这是刻意的取舍 —— 指标是滚动观测，
不是账本。要跨重启的长期趋势，那属于审计与外部监控系统的事。

实测验证过这一点：重启服务后 `提交 0 · 完成 0 · 拒绝 0`，
但 `nxs ops nodes` 里节点、批准状态全都还在（注册表是持久化的）。

---

## 五、暴露面：只给运维，不给节点

指标挂在 `/nxs/ops/metrics`，**节点密钥调用会被拒（403）**。

理由：指标是**拓扑画像**。

* "某节点每天处理多少任务"
* "拒绝集中在哪条规则"
* "谁在积压"

单独看每一项都不敏感，合起来就是一张网络规模与使用习惯的画像。
节点没有理由需要它 —— 它的视角应该只有自己的任务。

这与候选名单（`nxs candidates`）、审计"只记元数据"是同一条线：
**能不给的就不给。**

### 指标也不含业务内容

打点签名本身就是这道防线：`Metrics.on_submit` 只接受
`task_id` / `task_type` / `to_node`，**没有 `params` 参数** ——
想传内容进去都没有入口。`on_complete` 也不接收 `artifacts`。

有测试检查这两个签名（`test_metrics_contain_no_task_content`）。

## 六、怎么用

### 本机（开发 / demo）

```bash
nxs metrics
```

读的是**本进程内存**，所以只有同进程运行时才有数据。

### 远端（生产）

```bash
export NXS_OPS_SECRET=<与服务端一致>
nxs metrics --url https://nxs.example.com/nxs
```

### 喂给其他工具

```bash
nxs metrics --url ... --json | jq '.anomalies'
nxs metrics --url ... --json | jq '.totals'
```

数据形状（节选）：

```json
{
  "totals": {"submitted": 1, "completed": 1, "failed": 0, "denied": 4},
  "latency_ms": {"p50": 12.3, "p95": 45.6, "p99": 89.1},
  "latency_samples": 128,
  "by_type": {"work.calendar": {"completed": 1}},
  "denied_by_rule": {"MX-ISSUER-01": 2, "AU-NODE-04": 1},
  "nodes": [
    {"node_id": "work-laptop", "received": 1, "completed": 1,
     "pending": 0, "in_flight": 0, "capacity": 2,
     "backlog_ratio": 0.0, "bytes_out": 175, "failure_rate": 0.0}
  ],
  "anomalies": [
    {"rule": "probe_pattern", "severity": "critical", "subject": "hub",
     "message": "...", "rationale": "...", "suggestion": "..."}
  ]
}
```

### 阈值可调

"多少算多"取决于部署规模。全部阈值都在 `Thresholds` 里，
代码里用 `detect_anomalies(snap, thresholds=...)` 调整。

## 七、这个模块**不**做什么

诚实声明，避免误解：

* **不自动处置。** 只观测、只报告。熔断、暂停、吊销属于 M14 的运维动作，
  需要人做决定。让监控自己动手就违背了"人不被绕过"这条底线。
* **不做跨重启趋势。** 见第四节。
* **没有 Prometheus 导出。** 当前规模下 `--json` 足够。
  真需要时再加一个 exporter，不改本模块。
* **不监控宿主机。** CPU / 内存 / 磁盘不在范围内 ——
  那是 node_exporter 之类的工具该干的事，重复造会做得更差。

## 八、怎么复核

```bash
# 全部通过
.venv/bin/python -m pytest tests/test_observ.py -q

# 端到端：制造一次"试探"，看告警响不响（需先起服务）
nxs metrics --url http://127.0.0.1:18600/nxs
```

实测过的两个场景：

**① 权限试探**：一个节点撞到 3 种不同拒绝规则（`MX-ISSUER-01`、
`AU-NODE-04`、`MX-DOMAIN-02`）后，`probe_pattern` 以 `critical` 响起。

**② 先正常后卡死**（这个场景抓出了一个真 bug）：

```
① 正常跑了 3 笔：完成 = 3 | 异常: 无
② 卡死：投 6 个，一个都不领取
   待办: 8 | 累计完成: 3（不为 0，旧版会因此漏报）
   ● [critical] silent_stall: work-laptop 积压 8 个（并发上限 1，水位 8.0×），
     两次采样间产出 0（累计 3）
     evidence: {'produced_total': 3, 'produced_delta': 0, ...}
```

注意 `produced_total=3` 与 `produced_delta=0` 同时存在于 evidence 里 ——
前者说明"历史上干过活"，后者说明"这段时间没干活"。**判据必须用后者。**
