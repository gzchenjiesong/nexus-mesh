# Architecture

> 本文只描述**系统本身**：它是什么、由哪些模块构成、对外契约是什么。
> 不涉及任何具体部署场景。

---

## 1. 定位

Nexus Mesh 是一个**独立的协作基础设施**，面向**异构 Agent** —— 不同实现、
不同环境、不同信任域的 Agent，以各自的**身份、定位与角色**接入同一网络。

它与任何具体 Agent 都无耦合——协调节点自身也只是网络中的一个节点。
**替换任何一个节点（含人机入口）的实现，网络侧不需要改动**；这是
G4（与具体 Agent 解耦）的直接要求，也是 M1/M2 存在的理由。

它提供四件事：**注册能力**、**发现能力**、**投递与执行任务**、**可校验可追溯**。
它**不**决定任何业务：不决定谁该做什么，不决定任务怎么拆，不决定结果怎么用。

### 1.1 参与者

| 参与者 | 是什么 | 与网络的关系 |
|---|---|---|
| **Nexus Mesh** | 通信与协作的基础设施 | 本体。独立部署、独立演进 |
| **节点（Node）** | 一个以某角色接入网络的 Agent。有身份、有角色、有约束 | 网络中的一个节点，与网络之间只有协议关系 |
| **用户（User）** | 需求的提出者与决策者 | **不是节点**，经某个节点接入 |

"用户不是节点"这条约束是有意的：节点集合里永远只有 Agent。这样换一个人机入口
（换渠道、换实现）时，网络侧完全不需要改动。

### 1.2 四个核心抽象

| 抽象 | 是什么 |
|---|---|
| **节点（Node）** | 见上表 |
| **角色卡（Role Card）** | 节点的自我声明：角色、能力清单、信任约束 |
| **能力（Capability）** | 一个具名的任务类型，含参数 schema 与**应答字段白名单** |
| **任务（Task）** | 一次协作的载体，有状态机、租约、幂等键 |

四者的关系：

```
节点 ──注册──▶ 角色卡 ──声明──▶ 能力
                                  │
其他节点 ──按能力匹配──▶ 投递任务 ──▶ 应答边界 ──▶ 回传
```

**关键点：**节点集合完全由配置决定——加一个节点、加一个能力，
都不需要改动系统代码。这是它能否被称为"独立基础设施"的判据。

## 2. 三平面架构

采用网络架构的标准三分法。三者回答不同的问题、有不同的失败模式与演进节奏。

| 平面 | 回答 | 失败模式 | 演进节奏 |
|---|---|---|---|
| **控制面** | 该由谁执行？这次允许吗？ | 匹配错误、策略失效 | 改得最多 |
| **数据面** | 怎么送到？状态怎么记？ | 丢任务、重复执行、永久卡死 | 改得最少但要求最稳 |
| **管理面** | 规则是什么？发生了什么？ | 规则漂移无人察觉、无法追溯 | 需定期 review |

管理面**横切**前两者：它不参与运行时的任务流转，但决定流转规则并记录流转事实。

## 3. 模块

依赖方向严格单向：`Adapter(edge) → Core → Port ← Backend`。

**模块统一编号 M1–M14**；平面归属由小节标题表达，不占用字母前缀。
详细的编号体系（G/M/F/R/T + 横切标签）见 `CONTRIBUTING.md`「编号体系总览」，
功能点清单见 `traceability/registry.py`。

### 接入层（Adapter）

| 编号 | 模块 | 路径 | 职责 | 状态 |
|---|---|---|---|---|
| **M1** | 网关与认证 | `nxs/edge/auth` | HMAC 签名、时间窗、nonce 去重、凭据吊销、请求签名、限流与配额 | 已实现 |
| **M2** | 协议适配 | `nxs/edge/proto` | 与外部协议（如 A2A）互转 | 未实现 |

网关**不做业务判断**——"你能不能做这件事"是策略执行点的职责。

### 控制面（Core）

| 编号 | 模块 | 路径 | 职责 | 状态 |
|---|---|---|---|---|
| **M3** | 注册中心 | `nxs/control/registry` | 角色卡、能力索引、心跳与存活状态 | 已实现 |
| **M4** | 匹配器 | `nxs/control/matcher` | 按能力筛出候选执行者，**确定性排序** | 已实现 |
| **M5** | 策略执行点 | `nxs/control/policy` | **所有安全策略的唯一裁决处** | 已实现 |

### 数据面（Core）

| 编号 | 模块 | 路径 | 职责 | 状态 |
|---|---|---|---|---|
| **M6** | 信箱 | `nxs/data/mailbox` | 投递、拉取（拉取即加锁）、空队列 204 | 已实现 |
| **M7** | 任务生命周期 | `nxs/data/task` | 状态机、租约、超时释放、幂等去重 | 已实现 |
| **M8** | 会话与任务图 | `nxs/data/task`（`session_view`） | 会话上下文与任务依赖跟踪 | 部分实现 |
| **M9** | 产物通道 | `kind=reference` + 存储约定 | 大产物走**引用**不走内容 | 部分实现 |
| **M10** | 应答边界 | `nxs/data/boundary` | **字段白名单与等级上限的强制执行** | 已实现 |

> **D3 的设计红线**：它只**跟踪**任务图，绝不**决定**任务图。
> "怎么拆、发给谁"是发起方的职责。一旦网络开始决定怎么拆，它就退化成了中心编排器。

### 管理面

| 编号 | 模块 | 路径 | 职责 | 状态 |
|---|---|---|---|---|
| **M11** | 配置中心 | `nxs/mgmt/config` | 节点、矩阵、类型注册表、配额 | 已实现 |
| **M12** | 审计留痕 | `nxs/mgmt/audit` | 只记元数据，不记业务内容 | 已实现 |
| **M13** | 可观测 | `nxs/mgmt/observ.py` | 指标 + **只报组合异常**（无阈值告警） | 已实现 |
| **M14** | 运维接口 | `nxs/edge/gateway.py`（ops 端点）· `OpsClient` | 批准／吊销／释放租约／查节点／读指标 | 已实现 |
| **M15** | 观察窗 WebUI | `nxs/ui/server.py` · `nxs/ui/page.py` · `cmd_ui` | **只读**节点列表与系统汇总，token 鉴权，只听 127.0.0.1 | 已实现 |

### Port 与 Backend

| Port | 抽象的能力 | 候选 Backend |
|---|---|---|
| `QueueStore` | 持久化队列、原子取任务、租约 | memory / sqlite |
| `RegistryStore` | 角色卡存储、能力索引 | memory / sqlite |
| `AuditStore` | 审计写入与查询 | file |

Port 的价值是**可替换与可测试**（可用内存实现跑完整测试）。

> 注意：**这与"能否迁移部署"无关**。迁移靠的是本系统是**独立服务**——
> 各节点按配置重新连入即可。而 Python 运行时、PyYAML、数据库驱动这些
> 属于**部署依赖**，是系统自身实现带来的正常约束，不需要也无法清除。

## 4. 角色模型

角色按「**能力 + 约束**」定义，而非按「节点身份」。三个正交维度：

### 维度一 · 任务流向

| 角色 | 语义 |
|---|---|
| **Issuer** | 能拆解需求并发布任务 |
| **Executor** | 能接收、执行、回传（含追问） |
| **Relay** | 不执行业务，只转发 |
| **Observer** | 只读元数据，不能发布也不能执行 |

### 维度二 · 能力供给

**Provider**（提供具体能力）· **Aggregator**（组合多方结果）· **Decomposer**（拆解为子任务）

### 维度三 · 信任约束（与上两维正交）

**信任域** · **可达数据等级** · **可发布/可接收的类型集** · **配额**

> **"能力很强" ≠ "权限很大"。** 一个节点可以声明很多能力，
> 但 `max_response_level` 把它锁死在上限之内。这一维不可由能力推导。

### 角色卡

```jsonc
{
  "node_id": "node-a",
  "domain": "zone-a",
  "roles": { "executor": true, "issuer": false },
  "capabilities": [{
    "type": "demo.echo",
    "level": "metadata",                        // 该能力承诺的产出等级
    "mode": "sync",
    "params_schema": { "text": "string" },
    "response_fields": ["echo", "level"],       // ★ 应答字段白名单
    "freetext_fields": []                       // 自由文本字段（需单独声明）
  }],
  "constraints": {
    "max_response_level": "summary",             // ★ 硬上限
    "can_issue_types": [],                      // 空 = 不可发布任何任务
    "can_receive_from": ["hub"],                // 谁能给它派任务
    "can_delegate_to": [],                      // 空 = 不做二次委托
    "quota": { "tasks_per_day": 200, "concurrent_tasks": 1 }
  }
}
```

**两个字段值得特别注意：**

- `response_fields` —— "这个类型能返回哪些字段"在**注册时**固定，
  而不是运行时判断。这让越权字段成为结构事实。
- `can_issue_types: []` —— `roles.issuer=true` 只是"能力上可以"，
  真正的发布权限由这个白名单决定。关闭它可以避免**任务参数本身**
  成为数据外流通道。

## 5. 三重约束

一次应答是否放行，需要同时满足三个来源，**取最严**：

```
域间矩阵（这对域之间允许什么）
    ∩  节点自约束（这个节点不接受什么）
    ∩  能力声明（这个类型承诺产出什么）
    =  实际上限
```

举例：矩阵允许**片段级**，但某能力只声明**元数据级**，则实际上限是**元数据级**。

这三重之所以要分开，是因为它们由**不同的主体**决定：
矩阵由网络策略决定，节点约束由节点自己声明，能力声明由能力本身决定。
任何一方的宽松都不应放宽整体。

## 6. 应答边界

这是本系统区别于普通消息传递的核心。

### 数据分级

| 级别 | 内容 | 说明 |
|---|---|---|
| **元数据级** | `metadata` | 不含实体信息（"有这条记录""进度到某阶段"） |
| **摘要级** | `summary` | 经过抽象，**不含可还原原文的信息** |
| **片段级** | `fragment` | 原文的一部分，**具备还原价值** |
| **原文级** | `full_text` | 完整文件、对话记录、全文 |

### 两条实现原则

1. **拒绝到实现层。** 不该给的等级，不是"产出了再过滤"，
   而是**在节点侧根本不存在那条代码路径**。
2. **等级由产出方标注，调用方无法指定。**
   否则调用方可以直接"声明"自己只要摘要级，却实际拿到片段级。

### ⭐ 两层边界：分别回答两个不同的问题

这个区分是 v0.3 补上的，也是本系统安全模型成立的支点。

| 层 | 实现 | 回答的问题 | 需要的输入 |
|---|---|---|---|
| **节点侧** | `LocalBoundary` | **我能承诺什么** | 节点自己的角色卡 |
| **hub 侧** | `ResponseBoundary` | **你能得到什么** | 域 × 类型矩阵 + 全部角色卡 |

**为什么 hub 侧不够**：本系统的威胁模型是「**hub 被攻破**」。
那时 hub 上的任何检查都形同虚设——攻击者可以直接改代码跳过它。

所以真正保护数据的是**数据离开节点之前**那一次裁剪。两侧的差别很具体：

* hub 侧边界 = "发出去、被拒"
* 节点侧边界 = "**根本没发**"

测试里用记账 transport 验证这一点：越界产出时 `complete` 一次都没被调用。

**上限怎么算**：节点侧取 `min(卡片数据等级上限, 能力声明等级)`；
hub 侧取 `min(矩阵上限, 节点上限, 能力等级)`。两级取最小，
最终与单级三者取最小完全等价——**节点侧不放宽任何东西，只是把裁剪提前了**。

**降级模式**：节点没提供角色卡时，节点侧只能用产出等级兜底，
无法校验字段白名单（因为不知道白名单是什么）。此时 SDK **明确告警**，
不做"假装能检查"的处理——那会给出虚假的安全感。

### 拒绝语义

所有拒绝只返回 `rule_id` 与一条**固定消息**：

```json
{ "denied": "true", "rule_id": "WL-FIELD-001", "message": "response rejected" }
```

不含字段名、字段值、长度、前缀——**错误信息本身也是信道**。
细节只写本地审计日志。

## 6.5 自动匹配（M4）

不指定 `to_node` 时的派活路径：**匹配 → 排序 → 逐个过策略 → 取第一个通过的**。

### 两条硬约束

**① 排序必须确定性。** 同一输入两次必须选出同一个候选。

不是洁癖：分布式系统里"昨天能跑今天不能"是最难查的一类问题。
带随机性的话，你甚至无法确认改了一个东西之后是否真的修好了。
代价是负载均衡不如随机均匀——但本系统的前提是**"已知的少数节点"**，
那种成千上万对等节点的规模才需要随机化负载均衡。

四级排序键：

| 级 | 规则 | 理由 |
|---|---|---|
| ① | 同域优先 | 跨域数据流动本身是成本，能力相当时没理由舍近求远 |
| ② | 等级**刚好够用**优先 | 满足需求即可，不无故选一个能给更多原文的节点（最小权限） |
| ③ | 负载率低优先 | 用比率而非绝对数：并发上限 8 跑 3 个不比上限 1 跑 1 个忙 |
| ④ | 节点 ID 字典序 | **唯一目的是消灭不确定性** |

**② 匹配只看「能力 + 约束」，不看「关系」。**

这是 Mesh 语义与 Hub 语义的分界。匹配器**不读域间矩阵**：

| 视角 | 回答 | 输入 |
|---|---|---|
| 匹配器（单节点） | 我能不能干这个活 | 自己的角色卡 |
| 策略层（双方） | 这次委托允许吗 | 域矩阵 + 双方角色卡 |

实际好处：加一条矩阵规则**不会改变候选集合**，只影响"试到第几个才成功"。
两个变化源被隔开，排查时不必同时想两件事。
（有一条测试用 AST 扫源码，确保匹配器里没有 `check_*` 调用。）

### 候选名单是拓扑信息

"能执行 `work.calendar` 的节点有 3 个"这句话泄漏了网络规模与分布。所以：

* 候选名单**没有 HTTP 端点**（请求 `/nxs/candidates` 返回 501）
* 运维可在 hub 本机用 `nxs candidates --type <类型>` 看
* **匹配失败的错误码统一**：无论"没人有这能力"还是"有候选但全被策略拒"，
  对外一律 `WL-TYPE-404`。可区分就等于回答"确实有人能做，只是不给你做"

### 幂等必须早于匹配

`idempotency_key` 检查提到**所有校验之前**，并要求归属一致。

若不提前：自动匹配结果随负载变化，重试一笔**早已成功**的投递时
若候选恰好都不可用，会报"类型不可用"——调用方以为失败并做业务补偿，
那才是真正的重复副作用。

归属一致（命中任务的 `from_node` == 调用方）也是必需的：
否则猜到别人幂等键的节点就能通过这条快捷路径探到他人任务内容。

## 6.6 产物大小与 M9 的重新界定

**问题**：产物能带多大？答案不是读配置能得到的——三层限制里
有一层是死配置。实测见 [`artifact-size.md`](artifact-size.md)。

### 实测（不是推算）

| 文件 | 完整信封 | 结果 |
|---|---|---|
| 5 KB | 7 KB | ✅ |
| 100 KB | 134 KB | ✅ |
| **186 KB** | 254 KB | ✅ 临界 |
| 200 KB | 267 KB | ❌ `FM-BODY-04` |
| 10 MB | 13.3 MB | ❌ 差 50 倍 |

上限由 `server.max_body_bytes`（256 KB）决定，base64 固定膨胀 33%。

> ⚠ 顺带确认：节点配额里的 `bytes_per_response` **从未生效**——
> `check_quota(planned_bytes=...)` 在整个代码库里没有调用点。
> 它一直收默认值 0。这个遗留项记在 `config.py` 的 `UNIMPLEMENTED` 里。

### M9 不做"扩容"，做"引用"

设计文档早就定了 **"默认引用传递而非内容传递"**，`kind=reference` 就是它。
实测 10 MB 文件的坐标 payload 只有 **96 字节**——信封大小与文件大小无关。

**所以 M9 不是"大产物通道"，而是两个尚未实现的东西：**

| 缺口 | 现状 | 影响 |
|---|---|---|
| 一次性令牌 | 未做 | 接收方取坐标时没有受控通道 |
| `ArtifactStore` | 未做（Port 已定义） | 没有统一的产物存储抽象 |

而**跨网络的真正痛点不是带宽，是坐标能不能被对方访问**：
公司内网的 `/data/x.pdf`，云端 hub 根本摸不到。

这个缺口要不要补，取决于文件最终落在哪 —— 见 `artifact-size.md` 的决策表。
在需求明确之前不做，因为对象存储集成要引入凭据管理、生命周期与成本，
**在还没跑起来之前是过早优化**。

### 顺带修掉一个绕过

做这次实测时发现：`kind="freetext"` 曾是一个纯装饰字段。

节点可以声称 `kind=freetext`，而能力的 `freetext_fields` 为空 ——
此时清洗按**字段名**判断，看到空列表就直接原样返回。
于是注入文本未经处理就过关，而 `kind` 标签让接收方以为已经处理过。
**比不标更危险。**

现在 `check_kind_matches_declaration` 在**两层边界**都拒这种不符，
用的是同一个函数（两份实现迟早分叉，分叉那侧就是绕过口）。

## 6.7 可观测：只报组合异常

这节的标题就是设计结论：**没有单指标阈值告警**。

### 为什么阈值告警没用

| 形态 | 例子 | 问题 |
|---|---|---|
| 单指标阈值 | 响应字节 > 1MB | 正常的汇总任务天天触发 |
| 单指标阈值 | 请求频率 > 100/s | 正常批量任务天天触发 |

阈值告警的根病是**不知道上下文**：同一个数字在两种场景下含义相反。
告警响三天之后没人看了，真正的信号也就被淹掉。

设计文档的约束「告警要建在**系统级关联**上」说的正是这个：
判据必须是"单看正常、合起来可疑"的形态。

### `rationale` 是规则的资格证明

每条 `Anomaly` 都带一个 `rationale`，内容必须是
**"为什么单独看每个指标都不算异常"**。

写不出这句话的规则，说明它只是阈值告警，不该放在这个模块里。
有测试检查全部规则都填了 `rationale` 且包含"正常"二字。

### 五条规则

| 规则 | 组合条件 | 反例（不该报） |
|---|---|---|
| `bulk_movement` | 字节与完成量**同时**离群 | 只有字节大（汇总节点本来就产得多） |
| `probe_pattern` | 撞 **≥3 种**不同拒绝规则 | 反复撞同一条（那是配错） |
| `dead_route` | 节点离线**且**名下仍有任务 | 离线但没活（下班关机） |
| `silent_stall` | 积压 ≥3 倍上限**且**零产出 | 积压高但有产出（那只是忙） |
| `denial_dominance` | 拒绝率高**且**集中在单条规则 | 拒绝分散（那才是试探） |

注意后两条的配合：**集中的拒绝 = 配错（warn），分散的拒绝 = 试探（critical）**。
单看任一条都分辨不出来，两条一起才有分辨率。

### 与审计的分工

| | 审计 M12 | 可观测 M13 |
|---|---|---|
| 回答 | 三个月前谁派过活 | 现在健康吗 |
| 形态 | 落盘、可取证 | 内存、会丢 |
| 成本 | 扫文件 O(n) | 取快照 O(1) |
| 重启后 | 还在 | **归零** |

指标**不读审计日志**：按 10 万行 NDJSON 去算 p95，每次查询都要读整个文件。
把"看一眼监控"变成一次磁盘扫描，是设计错误。

重启归零是刻意取舍——指标是滚动观测，不是账本。

### 暴露面

`/nxs/ops/metrics`，**节点密钥调用被拒（403）**。指标是拓扑画像，
节点没有理由需要它。与候选名单、审计"只记元数据"同一条线。

指标也不含业务内容：`Metrics.on_submit` 的签名里**根本没有 `params` 参数**——
想传内容进去都没有入口。有测试检查这个签名。

详见 [`observability.md`](observability.md)。

## 7. 协作原语

| 原语 | 形态 | 适用 |
|---|---|---|
| **W1 请求-应答** | 发起 → 执行 → 回执 | 秒级、结果小。超时即失败，不重试 |
| **W2 提交-轮询-收取** | 提交 → 排队 → 租约 → 进度 → 完成 | 分钟级、结果大。**必须幂等** |
| **W3 扇出-聚合** | 一个需求 → 多个执行者 → 合成 | **跨域组合的唯一合法形态** |
| **W4 流水线** | A → B → C | 注意：数据等级**不得逐跳放宽** |
| **W5 委托链** | A → B → C（B 代表 A 发起） | 每跳权限**单调收窄**，绝不扩张 |
| **W6 长流程/补偿** | 多任务 DAG + 回退路径 | 网络提供依赖跟踪，发起方决定补偿策略 |

## 8. 设计原则

1. **只流转，不决策** —— 网络决定"怎么送"，节点决定"做什么"
2. **默认拒绝** —— 没有显式允许的即拒绝
3. **拒绝到实现层** —— 不是运行时过滤，而是没有代码路径
4. **只出不进** —— 协调节点不主动连任何节点
5. **不感知宿主与存储实现** —— 可替换、可测试
6. **不含任何 LLM 调用** —— 纯基础设施，不理解任务内容
7. **只记元数据** —— 审计不记业务内容，避免自己成为数据集中点
8. **断电恢复零人工干预** —— 租约超时释放 + 启动自检 + 幂等执行

---

## 9. 明确不做

| 不做 | 为什么 |
|---|---|
| 不含任何 LLM 调用 | 一旦它开始"理解任务内容"，就需要访问内容 |
| 不存业务数据与会话正文 | 只存元数据，保证自身被攻破时损失可控 |
| 不做内容层面的安全判断 | 注入检测、脱敏属于节点侧的应答边界 |
| 不决定任务拆解 | 那是 Decomposer 的职责 |
| 不提供面向用户的界面 | 加 UI 会让它变成应用而非基础设施 |
| 不实现完整 A2A 协议栈 | 只需信封语义对齐；真正对接交给协议适配器 |
| 不引入消息中间件 | 当前规模持久化队列足够 |
| 不保证业务正确性 | 只保证投递到、不重复、可追溯 |

## 10. 已知缺口

**这一节是刻意的、必须维护的。**

下面这些配置项会被正常解析、会被校验、会出现在 `nxs verify` 的输出里，
**但不会产生任何行为**。沉默地接受它们是危险的——使用者会以为自己
获得了某项防护。

约定三条：

1. 代码里的 `nxs.mgmt.config.UNIMPLEMENTED` 是**唯一权威清单**
2. `nxs verify` 与 `describe()` 会把它打印出来
3. `tests/test_architecture.py` 会核对本文件与那份清单一致

**新增配置项时，要么实现它，要么加进清单。**

| 配置项 | 缺什么 | 影响 |
|---|---|---|
| `params_schema` | 参数校验未实现 | **格式错误的参数会被投递出去**，由执行节点自己承担失败 |
| `bytes_per_response` | `check_quota(planned_bytes=…)` 无调用点，永远收 0 | **单次应答字节上限永不触发**。真实的体积硬上限是 `server.max_body_bytes`（约 186 KB 文件，见 [`artifact-size.md`](artifact-size.md)） |
| `bytes_per_day` | 应答字节数未按节点累计 | **按日字节配额永不触发** |
| `roles.relay` | 中继角色只声明、无实现逻辑 | 配 `relay: true` **不会**让该节点转发任务 |
| `roles.observer` | 观察者角色只声明、无实现逻辑 | 没有只读订阅通道 |
| `roles.executor` | **不构成准入闸门** | 设 `executor: false` **不会**阻止该节点领活与执行。真正的闸门是 `capabilities` 声明 |
| `roles.human_interface` | 只是分类标签 | 没有 Web UI、没有面向人的会话通道；人机交互走 CLI 与 SDK |

> ⚠ **`roles.executor` 这一行是 2026-10-27 实测后补的。**
>
> 直觉上 `executor: false` 像是"这个节点只发不收"的总开关，但它**不起这个作用**：
> 实测确认，一个 `executor: false` 但声明了能力的节点，能完整走完
> 投递 → 领取 → 执行 → 回传。
>
> 真正的准入闸门是 **`capabilities` 声明**：没有能力声明的节点，
> 投递会被策略层以 `WL-TYPE-404` 拒绝（也实测确认过）。
>
> 因此两者冲突时**系统相信 `capabilities`**——它是"我能做什么"（具体、可验证），
> 而 `roles` 是"我是什么角色"（抽象、分类）。相信更具体的那个是合理取舍，
> 但必须说清楚，否则人会以为关了开关。

> ⚠ **`bytes_per_response` 这一行是 2026-10-27 修的一处文档错误。**
> 原文写的是「按日字节配额永不触发（`bytes_per_response` 在策略层有效）」——
> 那句括号里的断言是**错的**：策略层确实有这项检查，但
> `planned_bytes` 参数在整个代码库里没有任何调用点，所以它永远收到 0。
>
> 这类错误比"漏记"危险得多：它明确告诉使用者"这项防护是有效的"，
> 而实际上完全不生效。发现方式是审计时顺着 `check_quota` 的调用点查下去。

> **v0.2 移出清单的三项**：`max_body_bytes`、`tls_cert / tls_key`、
> `rate_limit_per_second`。传输层落地后它们都真的产生行为了：
>
> * `max_body_bytes` —— 按 `Content-Length` **在读取之前**判定（超限 413 `FM-BODY-04`）
> * `tls_cert / tls_key` —— `ssl.SSLContext` 加载证书链并包裹监听套接字
> * `rate_limit_per_second` —— 网关认证后按节点做每秒计数（超限 429 `QT-RATE-04`）。
>   **必须在认证之后**，否则攻击者可伪造节点 ID 互相"借"配额。
>   固定窗口在边界允许 2× 突发，这是明确接受的代价；**不做滑动窗口**。
>
> ⚠ **但 TLS 有一条诚实的缺口：没有自动化测试覆盖。** 测试里需要自签证书，
> 而生成证书要引入 `cryptography` 依赖——为了一个测试破掉"运行时依赖仅
> PyYAML 一个"的纪律不划算。所以 TLS 目前**只经手工验证**。
> 这属于"验证强度的缺口"，不是"功能未实现"，因此不放在上表里混淆。

### 已知的验证强度缺口（不是功能缺口）

| 项 | 缺口 | 为什么接受 |
|---|---|---|
| TLS 握手与证书校验 | 无自动化测试 | 需引入证书生成依赖；手工验证过，且部署时才用 |
| 推送（SSE）在真实代理后的行为 | 无自动化测试 | 需要真实中间设备；已提供 `sse_enabled: false` 与短轮询降级路径 |

### 一处需要澄清的定位

设计原则说"Nexus 不做内容层面的安全判断"，但 `nxs/data/boundary.py`
确实做了内容处理（剥离指令性前缀、去控制字符、按字节截断）。

**这不矛盾，但需要说清**：

* `boundary.py` 虽然在同一个代码库里，**语义上属于节点侧组件**——
  它应当被部署在节点上，而不是协调节点上
* Nexus 核心（`control/`、`data/mailbox.py`、`data/task.py`）
  只做类型与字段层面的校验，不碰内容
* 它之所以放在同一仓库，是为了让 demo 能在单进程内验证完整链路

**未来的整理方向**：把 `boundary.py` 拆成独立的节点侧包（例如
`sdk/boundary`），使"哪些代码该部署在哪里"变得一目了然。
