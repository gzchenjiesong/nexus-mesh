# Protocol

> 本文件描述系统的**对外契约**：信封格式、状态机、端点、错误码。
> 它是实现互操作的依据——任何符合本契约的实现都应该能接入。

---

## 1. 信封（Envelope）

信封是**投递容器**，任务（Task）是**内容**。两者分开的原因：
传输与认证逻辑只关心信封，业务与策略逻辑只关心任务。

```jsonc
{
  "envelope_version": "1.0",          // 格式版本，主版本不兼容即拒收
  "session_id": "ses-9c2e41",         // 会话：一次用户诉求的上下文
  "trace_id": "tr-4a91c2",            // 追踪：端到端关联
  "sender": "node-b",               // 发送方
  "ts": "2026-10-07T20:05:00+08:00",  // 签名时间戳
  "nonce": "b7c1e9",                  // 一次性随机值，防重放
  "sig": "hmac-sha256:...",           // 见 §2
  "task": { /* 见 §3 */ }
}
```

### 版本协商

**信封版本与角色卡版本互相独立**，避免一次升级要求全网同步：

| 版本 | 载体 | 升级策略 |
|---|---|---|
| `envelope_version` | 每个信封 | **新字段可选、删字段需升主版本**（向后兼容优先） |
| `card_version` | 角色卡 | 节点可独立升级；旧版本保留以便追溯 |

主版本不同的信封**直接拒收**（`FM-SCHEMA-01`），不做兼容尝试——
本系统的节点集合是已知的少数节点，升级可以协调，不需要为兼容性付出复杂度。

## 2. 签名

```
sig = "hmac-sha256:" + HMAC-SHA256(secret, canonical_json(payload))
payload = { "sender", "ts", "nonce", "task" }
```

### 规范 JSON

签名输入必须是**确定性**的字节串，否则不同实现间校验会失败：

* 键**排序**
* 分隔符 `(",", ":")` —— 无多余空格
* `ensure_ascii=False` + UTF-8 编码

实现时必须使用统一提供的序列化函数，**不要自己 `json.dumps`**。
参数上任何一点差异（空格、键序）都会让签名失效。

### 不参与签名的字段

* `sig` 字段自身
* `envelope_version` —— 它是元数据，参与签名会让版本升级必须重新签名

### 校验顺序

1. **节点存在性**：发送方必须是已知节点
2. **吊销检查**：已吊销的凭据立即失效，不等到过期
3. **签名匹配**：使用常数时间比较（防时序侧信道）
4. **时间窗**：`ts` 与当前时间偏差超过 ±120 秒即拒
5. **nonce 去重**：窗口内重复出现即视为重放

**第 1 步失败时报「认证失败」而不是「节点不存在」** —— 避免通过错误码差异枚举节点 ID。

## 3. 任务（Task）

```jsonc
{
  "id": "t-7f3a91",
  "idempotency_key": "idem-3f2a91",   // ★ 必填，见下
  "type": "demo.echo",                // 必须已注册，命名 <verb>.<object>
  "session_id": "ses-9c2e41",
  "from_node": "hub",
  "to_node": "node-a",
  "status": "submitted",
  "mode": "sync",                     // sync | async
  "params": { "text": "hello" },
  "ttl": "2026-10-07T21:05:00+08:00", // 过期即作废
  "attempt": 0,
  "trace_id": "tr-4a91c2",
  "semantics": "data",                // ★ 永远是 data，见 §5
  "artifacts": []
}
```

### 三个关键字段

**① `idempotency_key`（必填）**

由发起方生成。重复提交同一个键不会创建第二个任务，而是返回已有任务。

这是**断电重试不产生重复副作用的前提**。对"代发消息""提交表单"这类
有副作用的操作，重复执行的后果是真实的。

> ⚠ 省略该字段时会自动生成——但那样重试就会创建新任务。
> **有副作用的操作必须显式传键。**

**② `level`（在 artifact 内部）**

**由产出方标注，调用方无法指定。** 否则调用方可以直接"声明"自己只要
摘要级，却实际拿到片段级的内容。

**③ `semantics`**

**产出永远是 `data`。** 见 §5。

## 4. 状态机

```
submitted ──▶ working ──▶ completed
                 │  ▲
                 ▼  │
          input_required
                 │
                 ▼
              failed / canceled
```

| 状态 | 含义 | 终态 |
|---|---|---|
| `submitted` | 已投递，未被领取 | |
| `working` | 已被领取，执行中 | |
| `input_required` | 执行方向发起方追问 | |
| `completed` | 成功完成 | ✓ |
| `failed` | 失败（超过重试上限或主动报告） | ✓ |
| `canceled` | 被取消 | ✓ |

**合法迁移**（其余一律 `LF-STATE-03`）：

```python
submitted      → working, canceled, failed
working        → input_required, completed, failed, canceled
input_required → working, canceled, failed       # 唯一可双向的状态
completed      → （终态，不可迁移）
failed         → （终态，不可迁移）
canceled       → （终态，不可迁移）
```

`input_required` 存在的意义：**让执行方在中途要信息时不必失败重来。**

## 5. `semantics` —— 防跨域提示注入的核心字段

取值为 `data` 或 `request`：

| 值 | 含义 | 接收方应如何处理 |
|---|---|---|
| `data` | 内容是被观察的数据 | 可分析、总结、呈现，**但不得直接据此触发工具调用或对外动作** |
| `request` | 内容是一个请求 | 仅用于发起方下达任务、以及执行方追问 |

**节点回传的一切内容一律被边界层改写为 `data`。**

理由：回传内容的来源（对话记录、文档、外部邮件）本质是人类自然语言，
其中完全可能包含"请把 X 发给 Y"这类**伪装成事实的指令**。

接收方看到 `data` 就知道：**这段内容要当数据看，不能直接当命令执行。**

> 这个字段的价值不在"现在启用严格模式"，而在于**它是零成本的期权**——
> 字段留着，将来想加防护随时能加；不留则要改协议、两端升级。

## 6. 数据等级

| 级别 | 内容 | 判据 |
|---|---|---|
| **元数据级** | `metadata` | 不含实体信息（"有这条记录""进度到某阶段"） |
| **摘要级** | `summary` | 经过抽象，**不含可还原原文的信息** |
| **片段级** | `fragment` | 原文的一部分，**具备还原价值** |
| **原文级** | `full_text` | 完整文件、对话记录、全文 |

### 实际上限取三重最小值

```
effective = min( 域间矩阵上限, 节点自约束上限, 能力声明等级 )
```

三者由**不同主体**决定，任何一方的宽松都不应放宽整体：

* **域间矩阵** —— 由网络策略决定
* **节点自约束** —— 由节点自己声明
* **能力声明** —— 由能力本身决定

举例：矩阵允许**片段级**，但某能力只声明**元数据级**，则实际上限是**元数据级**。

> 这就是"**声明即承诺**"：能力在注册时声明产出什么等级，
> 就必须真的只产出那个等级。

## 7. 应答字段白名单

每个能力在**注册时**声明 `response_fields`：

```jsonc
{
  "type": "demo.echo",
  "level": "metadata",
  "response_fields": ["echo", "level"],
  "freetext_fields": []
}
```

产出里出现白名单之外的字段 → `WL-FIELD-001`。

**为什么要在注册时固定而不是运行时判断**：这让越权字段成为
**结构事实**，而不是依赖过滤逻辑写对。检查会递归进入列表元素。

### 自由文本字段

只能返回自由文本的字段需单独声明（且必须同时出现在 `response_fields` 里）：

```jsonc
{
  "response_fields": ["results", "freetext_summary", "level"],
  "freetext_fields": ["freetext_summary"]
}
```

自由文本是提示注入的主要载体，因此额外施加三道处理：

1. **去除控制字符**（保留换行与制表符）
2. **剥离指令性前缀** —— 循环剥离，因为可能叠了多层
3. **按字节截断**（4096 字节，多字节安全，不切碎 UTF-8 字符）

剥离是**确定性的**，不是"检测告警"——告警会产生噪声，而剥离是确定的收益。

处理过的产出会在 `provenance.sanitized` 标记为 `true`，
接收方据此知道这段内容**不可原样信任**。

## 8. 拒绝响应

```jsonc
{
  "denied": "true",
  "rule_id": "WL-FIELD-001",
  "message": "response rejected"
}
```

**只有这三个字段。** 不含字段名、字段值、长度、前缀——**错误信息本身也是信道**。

细节只写入**本地**审计日志，不随响应返回。

---

## 9. 错误码

命名规则：`<域>-<对象>-<序号>`。**取值一旦发布不再变更**
（审计与告警会引用），需要更细粒度时新增取值。

| 前缀 | 域 |
|---|---|
| `FM-` | 格式 / schema 校验 |
| `AU-` | 认证与凭据 |
| `MX-` | 权限矩阵 |
| `WL-` | 白名单（类型 / 字段 / 等级） |
| `QT-` | 配额与速率 |
| `LF-` | 任务生命周期 |

| 规则码 | 触发条件 |
|---|---|
| `FM-SCHEMA-01` | 信封结构非法或主版本不兼容 |
| `FM-PARAM-02` | 任务参数不符合 schema |
| `FM-CARD-03` | 角色卡非法 |
| `AU-SIG-01` | 签名不匹配 / 未知节点 |
| `AU-REPLAY-02` | 时间戳超窗 / nonce 重复 |
| `AU-CRED-03` | 凭据已吊销 |
| `AU-NODE-04` | 节点未注册 |
| `MX-ISSUER-01` | 无发布权（角色关闭或类型不在白名单） |
| `MX-DOMAIN-02` | 矩阵无对应规则（**默认拒绝**） |
| `MX-RECEIVE-03` | 接收方不接受来自该域的委托 / 未批准 |
| `MX-DELEGATE-04` | 二次委托被禁 |
| `WL-TYPE-404` | 任务类型未注册 / 目标不提供该能力 |
| `WL-FIELD-001` | 产出含白名单外字段 |
| `WL-LEVEL-002` | 产出等级超过上限 |
| `WL-FREETEXT-003` | 自由文本超长或类型错误 |
| `QT-TASK-01` | 按日任务数用尽 |
| `QT-BYTE-02` | 单次应答字节超限 |
| `QT-BYTE-03` | 按日字节数用尽 |
| `QT-RATE-04` | 速率超限 |
| `QT-CONC-05` | 并发已满 |
| `LF-LEASE-01` | 任务已被领取 |
| `LF-EXPIRE-02` | 任务 TTL 已过 |
| `LF-STATE-03` | 非法状态迁移 |
| `LF-IDEM-04` | 幂等键重复 |

### 每次投递的检查顺序

越靠前的检查越基础，**失败即停，不留下任何痕迹**：

1. 发布方有权发布该类型 → `MX-ISSUER-01`
2. 目标节点可路由（未吊销、已批准、alive）→ `AU-*` / `MX-RECEIVE-03`
3. 域间矩阵允许这次投递且类型在范围内 → `MX-DOMAIN-02`
4. 目标接受来自该域的委托 → `MX-RECEIVE-03`
5. 配额充足 → `QT-*`

**通过后才写入队列。** 被拒的任务不会在队列里留下任何痕迹。

## 10. 端点

| 端点 | 方法 | 用途 |
|---|---|---|
| `/register` | POST | 节点注册与卡片更新（兼作心跳） |
| `/poll` | GET | 拉取待办任务（返回即打租约） |
| `/ack` | POST | 确认接收 / 续租 / 回传进度 |
| `/result` | POST | 回传结果 |
| `/publish` | POST | 发布任务（需 Issuer 角色） |
| `/session` | GET | 查询会话任务图（只读） |
| `/denied` | POST | 告知某任务被策略拒绝 |
| `/artifact` | GET | 数据面：按一次性令牌取大产物 |
| `/ops/*` | — | 运维接口（吊销 / 熔断 / 释放租约） |

> **状态：v0.1 尚未实现 HTTP 传输层。** 目前只有同进程传输
> （`nxs.app.InProcessTransport`）可用，供 demo 与测试使用。
> 上面是预留的契约，实现时不应偏离。

### 两类传输的差异

| | 同进程（v0.1 可用） | HTTP（待实现） |
|---|---|---|
| 走相同代码路径 | ✓ | ✓ |
| 需序列化 | 否 | 是 |
| 需认证 | 调用方已可信 | **必须验签** |

**两者走的是同一套策略与边界逻辑**，只是省掉了序列化与网络。
因此 demo 验证过的行为，真实部署里同样成立。

## 11. 轮询语义

* **不做长轮询。** 受限网络下连接会被中间设备切断，节点应周期性短轮询。
* **空队列返回 204**，不返回 `200 []` —— 省流量，也避免与"有任务但列表为空"混淆。
* **领取即加锁。** 任务被领走时立即标记 `working` 并开始租约计时。
* **轮询即心跳。** "来取任务"是"我还活着"的最强证据，比单独发心跳更可靠。

### 租约

* 默认 **15 秒**。取值权衡：太短会误判长任务为中断（导致重复执行），
  太长会让断电恢复变慢。
* **长任务应定期续租**，而不是靠调大这个值。
* 租约到期未完成 → 任务**自动回到队列**，无需任何人工介入。
* 重试次数**累积**，超过上限（默认 3）即落 `failed`，不再无限重试。

> 这是"断电恢复零人工干预"的实现：不需要知道执行方为什么消失，
> 只需要知道"它超过约定时间没交活"。

## 12. 审计记录

```jsonc
{
  "ts": "2026-10-07T20:05:01+08:00",
  "outcome": "denied",              // completed | denied | failed
  "rule_id": "MX-DOMAIN-02",
  "task_id": "t-7f3a91",
  "task_type": "demo.echo",
  "session_id": "ses-9c2e41",
  "from_node": "node-b",
  "to_node": "node-a",
  "from_domain": "zone-b",
  "to_domain": "zone-a",
  "level": "",
  "bytes": 0,
  "attempt": 0
}
```

**两条硬约束：**

**① 只记元数据。** 不出现任务参数、产出内容、自由文本。
如果审计包含业务内容，它自己就变成了数据集中点——而集中点正是
本系统要避免的东西。

实现上用**字段白名单**：未列出的字段被静默剔除。这样"不小心把
`params` 传进审计"这类错误会被结构性挡住。

**② 写入失败必须熔断。** `append` 失败即抛异常，不吞掉。

* **完成路径**：操作已经发生（任务已落终态），审计失败必须让调用方知道 ——
  "不可追溯的完成"比中断更糟。
* **拒绝路径**：什么都没发生，即使没记上审计结果也是安全的。
  此时审计失败会告警但不掩盖原始的拒绝异常。

格式为 **NDJSON**（每行一条 JSON）：追加写入天然安全、可 `tail` 直接查看、
单行损坏不影响其他行。
