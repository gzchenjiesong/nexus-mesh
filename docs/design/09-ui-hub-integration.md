## 〇·二、阶段 0 执行结果：根因与文档推测**不同**

> 2026-11-13 16:24 执行。结论：**不是锁死，是一个未认证的 DoS 漏洞。**

### 抓到的栈（`py-spy dump --locals`，完整版存 `/root/nexus-deadlock-20261113/`）

```
Gateway._serve_locked (gateway.py:428)        ← 单线程 accept 循环
  BaseServer.serve_forever (socketserver.py:238)
  SSLSocket.accept (ssl.py:1425)              ← accept 内部
    SSLContext.wrap_socket (ssl.py:517)        do_handshake_on_connect: True
      SSLSocket.do_handshake (ssl.py:1379)
        block:   False
        timeout: None                          ← ★ 无超时
      addr: ("14.212.83.239", 32509)           ← ★ 公网 IP
```

### 根因

`nxs/edge/gateway.py:680` 把**监听套接字**整体 wrap 成 SSL：

```python
httpd.socket = context.wrap_socket(httpd.socket, server_side=True)
```

而 Python 的 `SSLSocket.accept()` 内部会 **同步做 TLS 握手**
（`do_handshake_on_connect` 默认 `True`）。于是：

```
一个 TCP 连接建立（三次握手完成）
  → 但不发 TLS ClientHello
  → accept() 内部 do_handshake() 永久阻塞（socket 无超时）
  → serve_forever 单线程循环卡死
  → 后续连接全部排在 accept 队列（实测 Recv-Q=6）
```

**主线程还活着**（`ticks: 241834`，仍在跑 5 秒维护循环），
所以 systemd 认为服务健康 —— 这就是「静默」的来源。

### 已复现（不是推测）

用最小复刻脚本验证，三步：

```
① 正常 HTTPS            → 200 OK
② 建 TCP 但不发 ClientHello
③ 再来正常 HTTPS        → TimeoutError: _ssl.c:1015: The handshake operation timed out
   ⇒ 单个静默连接冻结了整个服务
```

**注意那个错误码：`_ssl.c:1015`** —— 与 2026-10-30 本机 `work-macbook`
桥接崩溃时的报错**完全相同**。那次是客户端侧超时，这次是服务端被冻结 ——
**同一个根因的两面。**

### 与文档推测的差异

| | 交接文档推测 | 实测 |
|---|---|---|
| 位置 | stale 标记路径的**锁获取** | **TLS 握手**（accept 循环内） |
| 性质 | 锁序死锁 | **未认证 DoS**：一个 TCP 连接即可 |
| 触发条件 | 多线程竞争（偶发） | 无需竞争，**必然** |
| 与 stale 从 1→3 的关系 | 因果关系 | **巧合**。主线程一直在跑，日志停只是因为它只在 `marked_stale>0` 时才打印 |

文档推测的依据（「stale 标记是唯一需要写锁的动作」）逻辑上合理，
但栈显示主线程根本没卡在锁上 —— 它在正常地 5 秒循环。
**卡住的是 gateway 线程，而它与 stale 标记无关。**

### 影响

| 项 | 值 |
|---|---|
| 严重度 | **高**。未认证、单连接、100% 可复现、静默 |
| 谁能触发 | 任何能连 18800 的人（该端口 `0.0.0.0` 对公网开放） |
| 本次实例 | 2026-10-31 18:19 起，持续 **13 天** |
| systemd 能否发现 | **不能**（主线程活着、无退出、无 CPU） |

### ⚠ 是谁发起的？—— 已查证：**外部，不是 nexus 节点**

这个问题必须先回答，因为它是「改客户端」还是「改服务端」的分界。

#### 逐个排除

| 候选来源 | 出口 IP | 排除依据 |
|---|---|---|
| `work-macbook`（开发机 Mac） | **103.7.29.9**（腾讯网段 `TENCENT-NET-AP-CN`） | ≠ `14.212.83.239` |
| `hermes-working` / `taskflow` | `127.0.0.1` | 它们配的是 `NXS_COORDINATOR_URL=https://127.0.0.1:18800/nxs`，走回环 |
| **`14.212.83.239`** | **中国电信**（`14.208.0.0-14.223.255.255`，abuse `anti-spam@chinatelecom.cn`） | 无反解、从未认证 |

#### 该 IP 的行为特征

| 检查项 | 结果 | 含义 |
|---|---|---|
| 审计记录命中 | **0 条** | 从未通过认证，纯 TCP 层 |
| 全系统日志命中 | **0 条** | 不扫 SSH、不扫其他端口 —— 不是横向扫描器 |
| 出现频次 | **1 次**（仅 11-13 抓栈时那一帧） | 一次性/低频 |
| 60 秒内 accept 队列增长 | **0**（10 次采样全 0） | 无持续高频扫描 |

#### nexus 客户端是否有能力产生这种连接

查 `nxs/edge/client.py`：

```
urllib.request.urlopen 调用次数:  4
手工 socket 操作（create_connection/wrap_socket）:  0
```

**客户端全部用高层 `urlopen`** —— TCP 连接与 TLS 握手由 urllib/ssl 内部连续完成，
**中间没有用户代码**，所以不存在「连上后长时间不发 ClientHello」的自然窗口。

唯一例外是进程在那一瞬间被冻结（笔记本休眠 / SIGSTOP）。但那属于
`work-macbook`，而它的出口 IP 是腾讯网段，**不匹配**。

#### 那它为什么能保持 13 天

`py-spy` 抓到的那一帧是按 `accept()` 内部拿到的**第一个**连接 —— 也就是
10-31 18:19 卡住时手上那个。此后 `serve_forever` 再没调用过 `accept()`，
所以它一直是同一个连接。

TCP 连接能活 13 天，最合理的解释：**发起方进程异常终止（被 kill -9 / 崩溃），
内核来不及发 FIN**，服务端那条就变成了孤儿半开连接。这是公网服务上的常见现象。

#### 但结论不是「所以不用修」

**恰恰相反。** 见下一节。

### 修复方向（待批准）

不要 wrap 监听套接字，改为在 `get_request()` 里逐连接握手并设超时：

```python
class _Server(ThreadingHTTPServer):
    def get_request(self):
        sock, addr = self.socket.accept()          # 裸 TCP，不在 accept 内握手
        if self.ssl_context is not None:
            sock.settimeout(HANDSHAKE_TIMEOUT)     # ★ 关键：超时
            try:
                sock = self.ssl_context.wrap_socket(sock, server_side=True)
            except (ssl.SSLError, OSError):
                sock.close()
                raise                              # 交给 serve_forever 记录并继续
            finally:
                ...
        return sock, addr
```

要点三条：

1. **握手必须可超时** —— 否则单连接冻结
2. **握手失败不能杀掉 accept 循环** —— 抛给 `_handle_request_noblock` 记录后继续下一条
3. 监听套接字**不再 wrap** —— 它不该带 TLS 状态

另需加一条守护测试：**建 TCP 不发 ClientHello，断言服务仍能正常响应**。
这条测试在修复前必须红（否则测不出问题）。

### 为什么「来源是外部」不改变「必须修」

用户的二分法（攻击 vs 实现问题）在这里有个陷阱：**两个答案不互斥，而且分界点不在这**。

真正的问题不是「谁发的」，而是：

> **为什么一个不需要任何凭据、不需要任何协议的静默 TCP 连接，
> 能让整个网络的协调节点冻结 13 天，而且 systemd 认为它健康？**

这跟来源无关。换成客户端 bug、换成机房网络抖动、换成某个忘记关闭的
`nc` 窗口 —— 结果完全一样。

**这是「默认行为脆弱」，不是「被攻击」。**

### 三个层次，优先级不同

| 层 | 问题 | 是否必须改 | 依据 |
|---|---|---|---|
| **服务端** | 握手不可超时，单连接冻结整个网络 | **必须** | 这是设计缺陷。任何公网服务都必须假设会收到畸形/半开连接 |
| **客户端** | —— | **不需要** | 已查证：客户端无手工 socket，不产生半开连接 |
| **防火墙** | 18800 对公网开放，机器在被大规模扫描 | 建议，但不阻塞修复 | 见下 |

#### 防火墙这层值得单独说

实测这台机器正被持续爆破：

```
SSH 失败登录尝试   11,240 次（10-25 至今 19 天）
独立攻击 IP        682 个
尝试的用户名       ubuntu / admin / user / deploy / test
                   / istrategycompass(!) / debian / oracle
```

注意 `istrategycompass` 出现 **19 次** —— 攻击者**已经知道这个域名/品牌**，
不是纯随机扫描。

`18800` 必须对公网开放（开发机 Mac 要从外面连），所以不能简单关掉。
可选措施：

| 措施 | 效果 | 代价 |
|---|---|---|
| 服务端修好（必做） | 单连接不再冻结 | 无 |
| 握手超时（同一处改动） | 半开连接自动回收 | 无 |
| 限制 18800 源 IP 白名单 | 大幅缩小暴露面 | 开发机出口是动态 IP（当前腾讯网段），会频繁失效 |
| 在云安全组限制 18800 | 同上 | 同上 |
| fail2ban 类联动 | 对 TLS 层难判定 | 收益低 |

**我的判断**：既然 `work-macbook` 需要从公网连、且出口 IP 不固定，
IP 白名单这类措施维护成本高。**把服务端修好是性价比最高的一条** ——
它同时解决「被扫到」和「自己出 bug」两种情况。

## 二、方案

### 总原则：**演进 `nxs/ui/`，不重写**

理由三条：

1. **现有 1142 行里藏着大量实机教训。** `page.py` / `server.py` 的注释里
   到处是「这是实机踩出来的」「第一版就是这么写的，结果……」。
   重写会把这些推理记录一起丢掉，而它们是这个代码库最贵的部分。
2. **§8 交付标准大部分已满足**（见上表：rationale / 最后更新 / 待批准 /
   待办 / 执行中 / 三块隔离 / 不读 sqlite / 只读）。真正的功能缺口只有 3 项。
3. **演进 = 同一个 service、同一个端口、同一个 unit 名** → hub 侧天然零改动。

### 阶段 0：先救活（前置，不可跳过）

| 步 | 动作 | 说明 |
|---|---|---|
| 0.1 | 装 `py-spy`，抓一份死锁栈 | **唯一的机会**。重启后现场就没了 |
| 0.2 | `systemctl restart nexus-mesh` | 恢复服务 |
| 0.3 | `curl -k .../nxs/health` + `nxs metrics --json` | 确认两件事都活（不只是 systemctl 说 active） |
| 0.4 | 按栈的复杂度决定：当场修 / 另立项 | 见决策 D1 |

> ⚠ 抓栈是**只读**操作（ptrace attach），不需要停机。装 `py-spy` 是唯一的
> 环境改动，可随时卸载。

### 阶段 1：补韧性（解决 ②）

我的建议比交接文档的「B + C」更收敛 —— **用内存快照代替落盘快照**（下称 B+D）：

| 组件 | 做法 | 是否违反铁律 |
|---|---|---|
| **B 本地探针** | 后端读 `/proc/<pid>/{stat,status,wchan}` + `ss` 端口 + `journalctl` 末行时间戳，回答「进程活着吗 / 卡在锁上吗 / 端口在听吗 / 日志还动吗」 | ❌ 不违反。这是**主机层可观测性**，不是业务数据 |
| **D 内存末次成功** | 面板在内存里保留最后一次成功的 ops 响应；coordinator 挂时展示它，并大字标注「最后已知状态 · N 分钟前」 | ❌ 不违反。数据仍只来自 ops 端点，且**不落盘** |

**为什么 D 比交接文档的 C（落盘快照）好：**

- C 要在磁盘上放一份业务数据副本 → 触碰「数据出口唯一」
- C 要设计 TTL、清理、陈旧判定
- 而**面板与 coordinator 同机**，coordinator 挂掉时面板通常还活着 —— 
  内存副本就够覆盖这个主场景
- 唯一覆盖不到的是「面板也重启了」，但那时本来也无从恢复；
  明说「面板刚重启，无历史」比给一份可能过期的数据更诚实

**展示行为（三态，不混排）：**

```
coordinator 正常      → 实时数据，角标「实时」
coordinator 不可达    → 顶部红色横幅「coordinator 不可达 · 已 N 分钟」
                       + 本地探针结果（进程/端口/wchan/日志末行）
                       + 灰显「最后已知状态（N 分钟前）」，与实时区视觉区分
面板刚启动且不可达    → 只显示探针结果 + 「无历史数据」
```

关键约束：**陈旧数据永不与实时数据混排**，且必须带时间戳。

### 阶段 4：上线与验收

| 项 | 做法 |

### 以下为原始决策分析（保留供追溯 —— 结论见 §4.0）


### D1 · coordinator 死锁的处理范围

| 选项 | 内容 |
|---|---|
| **A（推荐）** | 抓栈 → 重启 → **按栈的复杂度决定**是否当场修。若栈清晰（单一锁环）就顺手修；若涉及跨模块锁序则另立项 |
| B | 抓栈 → 重启 → 无论多复杂都当场修 |
| C | 只重启，不抓栈（放弃唯一的诊断机会） |
| D | 不碰 coordinator，先只做面板（但无法联调，只能盲写） |

我倾向 **A**。理由：死锁是**这个系统的高价值 bug**（13 天静默死亡、
systemd 都不知道），而面板的价值恰恰是「下次能看出它卡了」。
但**修死锁不该阻塞面板**——两件事可以并行。

⚠ 需要你额外同意：装 `py-spy`（只读诊断工具，`pip install` 到临时 venv，用完可删）。

### D2 · 「最需要时最没用」怎么解

| 选项 | 内容 | 代价 |
|---|---|---|
| A | 只显示「不可达 + 最后成功时间」 | 简单，但最需要时没信息（**现状**） |
| B | 加本地探针（进程/端口/wchan/日志末行） | 能回答「它卡了没」，看不到业务数据 |
| C | 落盘快照，挂时显示最后已知状态 | 触碰铁律②（磁盘上有业务数据副本） |
| **D（推荐）** | **B + 内存末次成功**（不落盘） | 覆盖主场景，不触碰铁律；面板自身重启后无历史 |

我推荐 **D**。这是对交接文档「B+C」的收敛 —— 
内存副本就够覆盖「coordinator 挂、面板还活着」这个主场景，
而落盘带来的铁律冲突与 TTL 复杂度都是不必要的代价。

如果你更看重「面板重启后也能看到历史」，那就选 C，我会加严格约束
（超 1 小时不显示、永不与实时混排、明确标注陈旧）。

### D3 · 替换还是并行

**建议：原地升级**（不是「替换」，因为演化的是同一个 service）。

- 端口仍是 8080，unit 名仍是 `nexus-mesh-ui`
- hub 的 `/api/nexus-enter`、Caddy、sites.json 全部零改动
- 无需新增子域

这其实是交接文档「替换」方案的更简版本 —— 连「停旧的、起新的」都不需要，
就是升级代码 + 重启。

### D4 · 重写还是演进

**建议：演进**（理由见「总原则」）。

若你希望借这次机会彻底重做前端（比如换技术栈），那是另一个量级的决定 ——
需要重新评估：现有 63 条 UI 测试要不要重写、`page.py` 里的实机教训怎么保留。

### D5 · 凭据收敛的范围

- 新代码：**必做**（建 `ui.env`，只放 OPS）
- 存量 `nexus-mesh-ui.service`：**建议顺带改**
  - 因为演进 = 同一个 unit，只改一行 `EnvironmentFile`
  - 但要重启服务（面板短暂不可用，几十秒）

若你希望存量服务保持原样（比如怕影响别的），我就只在新 unit 里做，
旧的不动 —— 但那样两个 unit 会并存，反而更乱。**建议顺带改。**

### D6 · token 交接方式

现状：hub 从 `journalctl -u nexus-mesh-ui` 抓 `t=<token>`。

我实测它**目前有效**：UI 至今只有 263 行日志，token 在 800 行窗口内。
但这是**脆弱的**：日志一多（比如异常 traceback 累积），token 会滚出窗口。

| 选项 | 内容 | 需改 hub？ |
|---|---|---|
| **A（推荐）** | 保持现状，不动 | 否 |
| B | 面板另写一份 token 到 `/run/nexus-mesh-ui/token`（tmpfs），hub 后续可改读文件 | 否（现在），将来是 |
| C | 去掉 token，只靠 Authelia + `Remote-User` 头 | 是 |

我推荐 **A：先不动**。理由：

- 它现在工作正常，改动收益小
- B 触碰铁律④（token 不落盘），需要单独论证
- C 会失去「Authelia 配错时的第二道防线」—— 而 `import guard` 
  存在的意义正是防止漏配认证。**不该把两道门减成一道。**

把它记为「已知的脆弱点」，等真有需要时再改。

### D7 · 设计 token 是否复用 hub

| 选项 | 内容 |
|---|---|
| **A（推荐）** | 复用颜色与圆角（`--ok/--warn/--bad/--accent`、12px 圆角），**布局独立** |
| B | 完全复用 hub 的设计系统（含布局语言） |
| C | 完全独立 |

推荐 A。理由：同一个人在两个页面间切换，配色割裂很刺眼；

现有面板的配色**已经合格**（交接文档逐项验算全部 ≥4.5:1），

## 六、阶段 2/3 上线后在生产发现的两个缺陷（2026-11-13）

两次缺陷都不是「代码写错了」，而是**守护测试守不住行为**。
记录在这里，因为它们比功能本身更值得记住。

### 缺陷 1 · 节点表读了错的数据源

部署完阶段 3a 后做生产验收，实测：

```
══════ ② 服务与数据 ══════
  nodes=3  stale=False  error=None
  单节点含新字段: backlog_ratio=False  bytes_out=False
```

节点表要的两半数据来自两个端点：

| 端点 | 视角 | 字段 |
|---|---|---|
| `/nxs/ops/nodes` | 身份/授权 | display_name、role、role_definition、capabilities… |
| `metrics.nodes[]` | 性能 | received、pending、backlog_ratio、bytes_out… |

前端只读 `ops/nodes`，读不到就被 `?? "—"` 静默降级成一个貌似正常的破折号。
**整张表 7 个格子全空，页面看起来没有任何毛病。**
顺手还发现吞吐列（received/completed/failed/pending/in_flight）**一直**是空的
—— 同一原因，只是此前没人核对过生产现场。

原有的守护是 `assert "backlog_ratio" in SHELL` —— **字段名在代码文本里
出现过就绿**。写成 `n.这个字段不存在` 也照样通过。

修法与守护：

- 服务端 `UiServer._merge_node_metrics()` 按 `node_id` 合并；有则覆盖、
  无则留空（留空而非填 0 —— 0 会被读成「真的没流量」）
- 合并发生在**存末次成功之前**，否则 coordinator 一挂水位列就集体变空
- 新守护是**契约**：从 `renderNodes` 抠出函数体，正则扫出每个
  `n.<字段>` 读法，逐个核对真实快照里有没有
- 反向验证：去掉合并 → 2 条红；改成按下标配对 → 串号测试红

### 缺陷 2 · 健康进程被报「疑似死锁」

同一轮验收，探针给出自相矛盾的结果：

```
verdict=healthy  unit=True  threads=2  queue=0
说明: 进程在、ops 端点可达
告警: ['阻塞在 futex_wait_queue · 阻塞在锁上（若持续如此，疑似死锁）']
```

逐线程实测真相：

```
tid=1080678  (main)  wchan=futex_wait_queue   ← 永久停在这里
tid=1080692          wchan=do_sys_poll        ← 真正在收连接
```

accept 循环在**后台线程**，主线程在等退出信号。连续 5 次采样（间隔 1 秒）
稳定如此，ops 每次正常响应 —— **futex 在这个架构里是稳态**。

根因是把告警写成 `if "futex" in wchan: warn("疑似死锁")`，单指标阈值。
这与 `observ` 模块「单指标告警必然误报」是同一条错误。

修法：读每个线程的 wchan，有线程在等 I/O 就说明 accept 循环活着；
只有组合信号（无 I/O 线程 / accept 队列在涨 / ops 不可达）成立才怀疑死锁。

⚠ **误报比不报更糟**：它训练人忽略 warnings，等真死锁来时没人看了。

### 共同的教训

两次都指向同一件事：**断言落在「某个词存在」上，守不住「行为对不对」**。

| 弱判据（不守行为） | 强判据（守行为） |
|---|---|
| `"backlog_ratio" in SHELL` | 前端读的每个字段，真实快照里都要有 |
| `"死锁" in _WCHAN_HINTS["futex"]` | 健康签名下**不许**产生死锁告警 |
| 预览用手写的固定 dict | 预览调用真实函数生成假数据 |

还有一条关于**预览**的：预览脚本两次都是因为自己拼假数据而"绿"。
凡是"预览/演示"类工具，其数据必须由真实实现生成，否则它验证的是自己。

## 七、Token 失效问题（2026-11-13 收尾）

用户要求「优先把 Token 的过期问题解决掉」。先查证，不猜 —— 结果发现
「过期」这个词与实现不符。

### 事实

**UI token 没有 TTL。** 它在 `UiServer.__init__` 里由
`secrets.token_urlsafe(32)` 生成一次，进程重启才变。所以失效只有两种成因：

| 触发 | 结果 | 那天发生的次数 |
|---|---|---|
| 服务重启（部署/改配置） | token 立刻换，旧标签全失效 | 5 次部署 = 5 次失效 |
| 浏览器关掉 | cookie 无 `Max-Age`，是 session cookie | 每次重开 |

同时查清：**从服务台进面板这条路本来就是自动的**。`nexus` 子域在
Authelia 两因素认证后面，卡片走 `/api/nexus-enter`（也在认证保护下）
从 journald 取最新 token 并 303 跳转。这条链路不会过期。

所以真正的缺口只有一个：**已打开的标签页失效后无法自助恢复。**
而当时的 401 页面在教用户「去服务器跑 journalctl」—— 可用户站在浏览器里，
手边没有终端。那是开发者视角，不是使用者视角。

### 解法（用户选定：失效即自动恢复，零安全妥协）

| 改动 | 解决什么 |
|---|---|
| 401 页面自动跳回 hub 的 `/api/nexus-enter`（3 秒倒计时 + 立即按钮） | 重启后被踢出 → 页面自己接上 |
| cookie 加 `Max-Age=30 天`（与 Authelia `remember_me: 1M` 对齐） | 关浏览器不用重取 |
| 只在 Host 是真实域名时给自动恢复 | SSH 隧道场景不该跳公网（可能连不通） |
| `recover_url` 严格校验（只收 http/https，拒 `<>"'` 空白反斜杠） | 它进 `href` 与 `<script>` 两个位置，配错一个引号就是 XSS |

**安全边界没动**：token 仍随机、仍重启即换、仍不落盘。recover 目标本身
在 Authelia 两因素后面，且会自己取最新 token —— 它拿到的是新凭据，
不是绕过校验。

### 防循环是重点

`401 → 跳 hub → 303 回面板 → 若又失效 → 401 → 跳…` 会变成每两三秒
自己刷一次的页面，比原来的"要手动取链接"糟得多。

用 `sessionStorage` 做 60 秒窗口：窗口内第二次**不跳**，改为告知
「刚尝试过自动恢复但未成功」。手动按钮始终可用（用户主动点是在表达意图）。

⚠ 第一版浏览器验证在这里出了假阴性：用两个 `newPage()` 测「第二次不再跳」，
而 `newPage()` 会新建 BrowserContext，sessionStorage 自然隔离 ——
第二条当然读不到第一条的标记。真实的循环发生在同一个标签页内。
**测「跨请求的状态保持」时，隔离环境的建法本身就会决定结论。**

## 八、两个部署缺口（同日发现，比上面所有功能问题更值得记）

这两件事的形态一样：**改的东西没生效，而所有输出都看起来正常。**

### 缺口 1 · 部署脚本从不安装 systemd unit

`deploy.sh` 只做「拉代码 → 重启 → 验证」，`/etc/systemd/system/*.service`
是**手工放**的，仓库里那几份只是源码留档。

于是给 UI 加了 `Environment=NXS_UI_RECOVER_URL=...` 之后：

```
$ tr '\0' '\n' < /proc/<pid>/environ | grep NXS_
NXS_OPS_SECRET=...          ← 只有这一个，没有 RECOVER_URL
```

代码是新的（cookie 的 Max-Age 生效可以证明）、服务 active、节点全在线 ——
**唯独那个新变量不存在**，token 恢复压根没启用。

修法：③b 段遍历 `deploy/*.service`，`cmp -s` 比较后不同才装 + `daemon-reload`，
位置在**重启之前**（否则这一轮跑的还是旧 unit）。

### 缺口 2 · 部署脚本自己有副本（鸡生蛋）

补上 ③b 后重新部署，输出里**没有那一段**。查证：

```
/root/nexus-mesh-deploy/deploy.sh   4664 字节   10-30 的版本
/opt/nexus-mesh/deploy/deploy.sh    5846 字节   已加 ③b
```

**改的是后者，执行的从来是前者。** 根因：部署脚本无法通过"部署"来更新
自己，所以当初在 `/root` 放了一份拷贝，然后静默分裂。

修法：`/root/nexus-mesh-deploy/deploy.sh` 改**薄壳**（只 `exec` 仓库那份），
其余同名文件改符号链接。薄壳源文件进仓库（`deploy/entrypoint.sh`）。

为什么用薄壳而非符号链接：仓库目录出问题时薄壳会明确说「仓库没拉到，
先 git clone」，而断链只会 file not found。

### 这两件事的教训

它们不报错、不告警、不影响服务启动。所有断言都绿：
代码是新的、服务 active、节点全在线。**只有"你以为改的地方"和
"实际生效的地方"是两个东西。**

靠"下次记得同步"解决不了 —— 那是靠记性，而记性在这里已经被证明会漏。
必须让**源头唯一**：unit 从仓库装、部署入口 exec 仓库那份。
