# 编号与命名体系规范

为「需求 → 架构 → 模块 → 功能 → 测试」建立一套**可追溯、可搜索、可自动校验**的编号体系。本规范基于与用户的讨论定稿，并已在本项目落地实施。

2026-10-08
 纵向 3 条链 + 横切 8 类
 已迁移 147 处标识符
 模块 M1–M14

## 00三条设计原则

#### ① 一字母只表示一件事

任何字母一旦承担两种含义，读者每次遇到都要消歧。而这个成本会随时间累积——旧引用还在，新人不了解历史，于是歧义越滚越大。**宁可多用一个字母，也不让一个字母兼职。**

#### ② 编号即坐标，不是序号

编号的价值在于**能反过来定位到东西**。看到 `M7.F2` 就应该知道去哪个文件找；看到 `L1` 却只能猜。**无法被搜索的标识符，在维护时等于不存在。**

#### ③ 能自动校验的才可信

靠人记住的规范必然腐烂——不是有人故意违规，而是没人能一直记得。**每条规范都应有一条测试守护**，否则它只是一段愿望。

## 01问题诊断（实测）

在定这套体系之前，我先扫描了项目里**实际占用**的编号前缀。结果是：**14 个字母被占用，其中 6 处冲突**。

### 1.1 实测占用情况

| 字母 | 当时含义 | 出现次数 | 冲突判定 |
|---|---|---|---|
| **L** | 数据等级 L0–L3 | 309 | 致命 与"严重等级 Lx"冲突，且已固化进代码枚举 |
| **N** | 待定项 · 明确不做（**双义**） | 73 | 需消歧 |
| **M** | 管理面模块 · v0.1 待办（**双义**） | 60 | 需消歧 |
| **P** | 落地阶段 P0–P4 | 53 | 需让位 与"优先级 Px"冲突 |
| F | 功能要求 F1–F17 | 34 | 一致 |
| S | 安全要求 S1–S10 | 32 | 一致 |
| **D** | 数据面模块 D1–D4 | 31 | 高 与"设计需求 Dx"冲突 |
| Q | 待确认项 Q1–Q9 | 25 | 保留 |
| **A** | 架构纪律 A1–A8 | 25 | 并入 C |
| **C** | 控制面模块 C1–C3 | 25 | 高 与"代码准则 Cx"冲突 |
| W | 协作原语 W1–W6 | 17 | 保留独立 |
| **E** | 接入层模块 E1–E2 | 12 | 并入 M |

### 1.2 根因诊断

> **冲突的根源不是"字母不够用"，而是"模块用了四套前缀"。**

当时模块按**所在平面**分组编号：接入层 `E1–E2`、控制面 `C1–C3`、
数据面 `D1–D4`、管理面 `M1–M4`。
看似"按平面分组更清晰"，实际代价是**一次性吃掉四个字母**，
而这四个字母恰好都是其他体系想用的（C 想给代码准则、D 想给设计需求、E 想给证据强度、M 想给里程碑）。

于是四套体系叠在同一个字母空间里必然相撞。

> **解法：模块统一编一个序列，平面归属改为「编号区间 + 属性列」。**

`M1–M2` 就是接入层，`M3–M5` 就是控制面 —— 这个信息
写在模块表的"平面"列里，**不需要占用字母前缀表达**。
一次出让四个字母，冲突面立刻收窄。

## 02完整体系

### 2.1 纵向分解：三条链路

```
┌─ 目标层 ─────────────────────────────────────────────┐
G1 … G5   Goal 设计目标 —— 系统存在的理由
└──────────────────────┬───────────────────────────────┘
                       │ 分解为
┌─ 模块层 ─────────────▼───────────────────────────────┐
M1 … M14  Module 模块 —— 统一编号，平面归属写在属性列
└────────┬─────────────────────────────┬───────────────┘
         │ 实现视角                     │ 约束视角
┌────────▼──────────┐        ┌─────────▼───────────────┐
F  功能点            │        │ R  模块需求              │
│  判据：有代码逻辑    │        │  判据：约束/质量属性      │
│  M7.F2            │        │  M7.R1                  │
└────────┬──────────┘        └─────────┬───────────────┘
         │ 验证                        │ 验证
┌────────▼─────────────────────────────▼───────────────┐
T  测试用例 —— 挂 F（功能验证）或挂 R（跨 F 的聚合验证）
   M7.F2.T1                          M7.R1.T3
└──────────────────────────────────────────────────────┘
```

> **关键：F 与 R 是两条平行链路，不是层级关系。**

这一点是用户提出的，比我最初的方案准确。我原来把 R 和 F 做成了层级（M → R → F → T），
但那样会漏掉一类真实存在的测试——**跨 F 的聚合测试**。

典型例子：约束「**断电恢复必须零人工干预**」需要四个功能点协同才能成立
（租约超时释放 + 启动自检 + 幂等执行 + 长任务续租）。
验证它的那个端到端测试**测的是这个约束，而不是任何单个功能点**。
如果 R 是 F 的父级，这类测试就只能硬塞进某个 F，而那是错的。

> **关于 E 的一次反复，值得记下来。**

E 从"接入层模块"让位后，我一度把它分配给"证据强度"（写作 E0–E4）。
但那是**另一个方向的重蹈覆辙**——E 只是一个空闲字母，并不是为"证据"准备的。

在与用户确认后改为**直接用词**（对抗 / 端到端 / 单元 / 静态 / 仅声明）。
教训：**"字母空着"不等于"可以给它派个用途"。**
一个字母的正当性来自"有东西必须用它来指代"，而不是"它还没被占用"。

## 03纵向分解详解

### 3.1 G · 设计目标（已定稿）

从系统定义文档反推，Nexus Mesh 的设计目标共 5 条。**每一条都必须是"可判定的"**——否则它无法派生后续的 M/R/F。**用户已确认全部 5 条。**

| 编号 | 目标 | 可判定的形式 |
|---|---|---|
| **G1** | 让异构 Agent 能协作 | 不同框架/厂商构建的 Agent，可以在不共享内部状态的前提下发现彼此、委托任务、回传结果 |
| **G2** | 让协调节点被攻破也不泄露原始数据 | 攻击者完全控制协调节点后，经本网络仍**无法获取任何节点的原始数据** |
| **G3** | 让每次协作可校验可追溯 | 任何一次委托都能回答：谁、何时、向谁、发了什么类型的任务、命中了哪条规则、结果是什么等级 |
| **G4** | 与任何具体 Agent 解耦 | 替换任何一个节点（含人机入口）的实现，网络侧不需要改动 |
| **G5** | 节点集合变化不需要改代码 | 新增/移除节点、新增任务类型，只改配置，代码零改动 |

> **G2 与 G5 是这套体系的价值所在。**它们不是"功能"，而是"约束"——
它们决定了架构长什么样（应答边界、默认拒绝、配置驱动）。
如果只写 G1 和 G3，很容易设计成一个普通的消息队列。

### 3.2 M · 模块（M1–M14）

从原来的四套前缀（E/C/D/M）合并为统一序列。**平面归属由"编号区间 + 属性列"表达，不再占用字母前缀。**

| 新编号 | 模块 | 原编号 | 平面 | 实现状态 |
|---|---|---|---|---|
| **M1** | 网关 Gateway（含认证） | E1 | 接入层 | 部分 仅 `edge/auth.py` |
| **M2** | 协议适配 Protocol Adapter | E2 | 接入层 | 未实现 |
| **M3** | 注册中心 Registry | C1 | 控制面 | 已实现 |
| **M4** | 匹配器 Matcher | C2 | 控制面 | 未实现 |
| **M5** | 策略执行点 PEP | C3 | 控制面 | 已实现 |
| **M6** | 信箱 Mailbox | D1 | 数据面 | 已实现 |
| **M7** | 任务生命周期 Task Lifecycle | D2 | 数据面 | 已实现 |
| **M8** | 会话与任务图 Session | D3 | 数据面 | 部分 仅会话视图 |
| **M9** | 产物通道 Artifact Channel | D4 | 数据面 | 未实现 |
| **M10** | **应答边界 Response Boundary** | 新增 | 数据面 | 已实现 |
| **M11** | 配置中心 Config Store | M1 | 管理面 | 已实现 |
| **M12** | 审计留痕 Audit Trail | M2 | 管理面 | 已实现 |
| **M13** | 可观测 Observability | M3 | 管理面 | 未实现 |

> **为什么是 14 个而不是原来说的 13 个：**

第 10 号「**应答边界**」原本不在模块列表里——这是审查中发现的缺口：
它以 `nxs/data/boundary.py` 的形式存在于实现，也承载着 G2（核心目标），
却从未被列为模块。既然要统一编号，正好把它补进来。

### 3.3 F · 功能点

> **判据：有对应的代码逻辑。能用一句话描述"它做了什么"。**

反例：「系统必须高效」——没有代码逻辑，不是 F。
正例：「租约超时后任务自动回到队列」——有实现、可测试，是 F。

### 3.4 R · 模块需求

> **判据：是约束或质量属性；可能横跨多个 F；可能没有独立的代码实现。**

R 与 F 的边界容易模糊，用两个问题区分：

> 2. **它有独立代码吗？**有 → F；没有（靠若干 F 共同满足）→ R
> 4. **它能被单个测试直接验证吗？**能 → F；需要聚合多个功能才能验证 → R

> **R 与 C 的边界**（这条容易混）：

> - **C** —— 适用于**多个模块**的准则（如"拒绝时不得泄露内容"适用于任何会拒绝的模块）
> - **R** —— 只适用于**某个模块**的要求（如"策略执行点必须默认拒绝"）

> **判据：如果一个约束换个模块也成立，那它是 C，不是 R。**

### 3.5 T · 测试用例

| 挂载点 | 编号形式 | 适用 |
|---|---|---|
| 挂 **F**（功能验证） | `M7.F2.T1` | 验证单个功能点的行为 |
| 挂 **R**（约束验证） | `M7.R1.T3` | 需要多个 F 协同才能验证的聚合测试 |

> **为什么要分两种挂载点：**因为有一类测试的"被测对象"是约束本身。
比如「租约恢复」的端到端测试，它需要 F1（超时释放）+ F4（启动自检）同时正确。
把它挂在 F1 上会让读者以为"只要 F1 对，这个测试就该过"——那是错的。

### 3.6 层级编号的写法

```
M7                 模块
M7.F2              模块 7 的第 2 个功能点
M7.F2.T1           上者的第 1 个测试用例
M7.R1              模块 7 的第 1 条需求（与 F 平行）
M7.R1.T3           上者的第 3 个测试用例（可能是跨 F 的聚合）
```

> **层级深度上限：3 段（M / F|R / T）。**

用户最初提议过 `T1-1-1-5` 这种四段形式。我不建议再往下拆，两个理由：

> - **可读性** —— 四段编号在口头沟通与代码注释里已经难以念清
> - **F 已经足够细** —— 如果某个 F 还需要再拆子功能，说明它拆得不够细，应该拆成两个 F

> **分隔符统一用点号（`.`）**，不用斜杠或短横——点号在编程语境里更自然，且不与错误码的短横冲突。

## 04横切标签详解

### 4.1 S · 安全要求

违反即"系统存在的意义不成立"。当前 10 条（S1–S10），全部与 G2 相关。

### 4.2 N · 明确不做

> **反向要求，与正向要求同等重要。**只列"要做什么"的文档读起来像营销材料；
而"不做什么"定义了边界——多做的每一件事都是攻击面与维护负担。

当前 9 条（N1–N9）。其中 **N3 明确不做内容层面的安全判断**、
**N7 不引入消息中间件** 这两条最容易被无意违反。

### 4.3 C · 代码准则

全局性工程约束，8 条（C1–C8）。每条都有对应测试守护，详见 `CONTRIBUTING.md`。

| 编号 | 准则 | 守护测试 |
|---|---|---|
| **C1** | 术语统一 | `TestTerminology`(5) |
| **C2** | 分层纪律（依赖单向） | `TestLayerDirection` · `TestCoreHasNoIO` |
| **C3** | 不得出现任何节点的名字 | `TestNoNodeHardcoding`(4) |
| **C4** | 拒绝时不得泄露内容 | `TestDenyNeverLeaks`(2) |
| **C5** | 默认值落在"拒绝"一侧 | `TestDefaultsAreDeny`(4) |
| **C6** | 严格校验，拒绝未知字段 | `TestStrictValidation`(6) |
| **C7** | 配置字段必须被使用 | `TestConfigFieldsAreUsed`(3) |
| **C8** | 标识符命名：禁止短编号式 | `TestIdentifierNaming`(4) |

### 4.4 P · 优先级

P0（必须）/ P1（应该）/ P2（可以）/ P3（暂缓）。**它是标签而非标识符**——用于排期与评审，不进入代码。

### 4.5 SEV · 严重等级

> **为什么不用 L：**数据等级曾用 `L0–L3`，验证强度曾用 `L0–L4`。
如果严重等级再用 `Lx`，就会出现三套 L 并存。

**为什么用 SEV 而不是 S：**S 已被安全要求占用（S1–S10）。
SEV 是业界通用写法，且因为有两字母以上，不会与单字母体系产生视觉混淆。

### 4.6 Q · 待确认

需人工决策的问题（Q1–Q9）。已在既有文档中形成的惯例，保持不变。

### 4.7 MS · 里程碑

吸收原"落地阶段 P0–P4"。**必须从 P 改到 MS**——因为 P 是优先级，而"阶段"与"优先级"是两件事： 一个阶段的优先级可能是 P0，但它本身不是 P0。

### 4.8 W · 协作原语

W1–W6，**保留独立分类**（用户确认）。它既不是需求也不是模块，而是"系统支持的交互模式"—— 是 G1 的具体能力清单。

### 4.9 证据强度：为什么不给它字母

> 审查报告中评估"验证是否足够"时用了一个五级尺度：
**对抗 / 端到端 / 单元 / 静态 / 仅声明**。
它曾写作 L0–L4，中间一度改为 E0–E4。

**最终结论：它不该占用字母，直接用词。**理由——

> - 它不是项目里反复引用的**实体标识**（不像 M7、F2 那样能定位到东西）
> - 它只在**审查报告内部**用于评估，不进入代码、配置或协议
> - 给它分配字母，就是在鼓励它被误当成编号体系的一部分

> **结论：仅在审查文档中以「对抗 / 端到端 / 单元 / 静态 / 仅声明」这五个词称呼它，不缩写。**

## 05C8 标识符命名

> **这条规范由用户提出，是本次体系调整中最有实际价值的一条。**

### 5.1 问题

> **用户的判断：**"我不希望代码里面有这么精简的变量……太短的代码变量对于后续的搜索非常不友好。"

这个判断是对的，而且比他说的还严重一点。以 `Level.L0` 为例：

> - **搜索失效** —— `grep L1` 会命中十六进制串（`0xL1` 形态）、 变量名片段（`URL1`）、注释里的其他编号、无关的自然语言。 而 `grep summary` 能精确定位
> - **体系冲突** —— 与"验证强度 L1"、"严重等级 L1"三者不可区分
> - **日志不可读** —— 运维看到审计日志里的 `"level": "L1"` 必须查表才知道含义

### 5.2 正确做法：三层命名

| 层 | 形式 | 用途与理由 |
|---|---|---|
| **代码标识符** | `Level.SUMMARY` | 属性访问、IDE 补全、grep 定位 |
| **线上值** | `"summary"` | 写进信封、配置、审计日志。自解释，无需查表 |
| **中文表述** | 摘要级 | 面向人的文档与讨论 |

> **关键设计：代码标识符与线上值用同一个名字**（节点名的小写形式），不引入映射表。

映射表会腐烂——每加一个等级就要记得改两处，而漏改不会报错。
**同一个名字不会腐烂。**

### 5.3 迁移对照

| 旧 | 代码标识符 | 线上值 | 含义 |
|---|---|---|---|
| L0 | `Level.METADATA` | `"metadata"` | 元数据：不含实体信息 |
| L1 | `Level.SUMMARY` | `"summary"` | 摘要：经抽象，不含可还原原文的信息 |
| L2 | `Level.FRAGMENT` | `"fragment"` | 片段：原文的一部分，具备还原价值 |
| L3 | `Level.FULL_TEXT` | `"full_text"` | 原文：完整文件、对话记录、全文 |

### 5.4 旧写法兼容

`Level.parse` 仍接受 `"L1"` 这类旧写法， 但会发出 `DeprecationWarning`。**刻意不静默接受**—— 静默兼容会让旧写法永远留存在配置里，而每次解析都要多走一次映射。

## 06完整示例

用真实的模块 **M7 任务生命周期**走一遍完整链路。

```
# 目标层
G2  让协调节点被攻破也不泄露原始数据
G3  让每次协作可校验可追溯

# 模块层（M7 服务于 G2 与 G3）
M7  任务生命周期 Task Lifecycle    平面=数据面   实现=nxs/data/task.py

# ── 约束视角（R）：这个模块必须满足什么 ──────────────
M7.R1  断电恢复必须零人工干预            ← 约束，无独立代码，需多 F 协同
M7.R2  重试不得产生重复副作用            ← 约束，由 F2 落实
M7.R3  长任务不得因租约到期被误判为中断     ← 约束

# ── 实现视角（F）：这个模块做了什么 ──────────────────
M7.F1  租约超时后任务自动回到队列          ← 有代码：release_expired()
M7.F2  幂等键阻止重复提交                  ← 有代码：submit() + 后端唯一约束
M7.F3  状态机拒绝非法迁移                  ← 有代码：_transition()
M7.F4  重试次数累积，超限落 failed         ← 有代码：release_expired() 的判定
M7.F5  长任务可续租                        ← 有代码：renewal_deadline()

# ── 验证层（T）─────────────────────────────────────
## 挂 F 的：验单个功能点
M7.F2.T1  同一幂等键重复提交 → 返回已有任务
M7.F2.T2  幂等键冲突不覆盖已有状态（回归测试）
M7.F3.T1  completed → working 被拒
M7.F3.T2  input_required ↔ working 双向可通

## 挂 R 的：验约束（需多个 F 协同）
M7.R1.T1  执行方被 kill → 租约超时 → 任务回队 → 重启续跑（跨 F1+F4）
M7.R2.T1  断电重试后副作用只发生一次（跨 F2+F4）
```

> **这个例子里最关键的一处：**

`M7.R1.T1`（断电恢复的端到端测试）**不能挂在 F1 上**——
它同时需要 F1 的租约释放与 F4 的重试上限判定正确。
如果挂在 F1，将来有人改动 F4 导致这个测试失败，会让人误以为是 F1 坏了。

**挂在 R1 上则语义准确：它测的是"零人工干预"这个约束。**

## 09守护机制

> **一条规范如果没有测试守护，它只是一段愿望。**

这是本项目已经吃过的教训：`MatrixRule.allow_issue` 曾被写进配置与文档，
却从未被任何逻辑读取——它"存在于规范里"，但没有任何东西阻止它失效。

| 规范 | 守护测试 | 触发条件 |
|---|---|---|
| C1 术语统一 | `TestTerminology` | 代码/配置/文档出现废弃术语 |
| C3 无节点硬编码 | `TestNoNodeHardcoding` | 源码出现节点名/域名/类型名 |
| C7 配置字段被使用 | `TestConfigFieldsAreUsed` | 字段只被解析、未被属性访问 |
| **C8 标识符命名** | `TestIdentifierNaming` | 标识符形如 `L0`/`D1`/`T12` |
| 依赖最小化 | `TestDependencyFootprint` | 运行时依赖超出白名单 / 出现禁依赖 |

> **待补的守护（当前靠人工）：**

> - **编号引用有效性** —— 无法检测"引用了不存在的 M99"或"废弃编号仍被引用"
> - **F/R 的覆盖完整性** —— 无法检测"某个 F 没有任何测试"
> - **层级编号格式** —— 无法检测 `M7-F2-T1` 这种用错分隔符的写法

> 建议的实现方式（v0.2）：用装饰器把编号挂在测试上，再加一个元测试校验引用有效性与覆盖完整性。
**这样追溯表是"跑"出来的，不是"抄"出来的。**

这是本次最实质的产出 —— 追溯不是写在文档里，而是**可校验的**。

```
┌─ 唯一真相源 ───────────────────────────────────────────┐
traceability/registry.py    编号清单（G/M/F/R/C/N/S）

└────────────────────────┬───────────────────────────────┘
                         │ 被以下两者引用

tests/test_*.py              @covers("M5.F1")  测试声明覆盖
tests/test_traceability.py  元测试：校验两边一致
└────────────────────────┬───────────────────────────────┘
                         │ 自动生成
┌────────────────────────▼───────────────────────────────┐
traceability/MATRIX.md       追溯矩阵（勿手工编辑）
└────────────────────────────────────────────────────────┘
```

#### 元测试校验的五件事

2. **编号格式合法** —— `M5.F1` 而非 `M5-F1`（短横线留给错误码）
4. **引用有效** —— `realized_by` 指向的 F 必须真实存在
6. **覆盖完整** —— 每个 F / R / C 至少被一个测试覆盖
8. **无孤儿引用** —— 测试里挂的编号在清单里必须存在（防改名后留死引用）
10. **无沉默测试** —— 每个测试都必须声明 `@covers`

> **为什么必须"可执行"：**手写的映射表必然腐烂。
不是有人故意违规，而是没人能一直记得 —— 改了代码忘了改文档，
而**漏改不报错**，于是映射表慢慢变成谎言。

这与 C7（配置字段必须被使用）是同一个道理：**凡是被声明出来的东西， 都要有地方校验它。**

#### 过程中元测试抓到的两个真问题

① 元测试会误报：只跑单文件时"全部未覆盖"

初版元测试依赖 pytest 的收集结果（`request.session.items`）。
 但开发者常只跑单个文件 —— 此时 session 里没有其他文件，
 元测试会误报"66 个编号项全部未覆盖"。

 **一个会误报的检查比没有检查更糟，因为它会让人不再相信它。**

✓ 改为**直接 AST 扫描测试源码**提取 `@covers`，不依赖收集范围。任何调用方式下结论一致。

② 上一轮声称存在的测试实际从未写入

审查报告中声称新增了 `TestConfigFromEnvironment`(3)，
 但追溯扫描时发现**该测试类实际不在文件里** ——
 上一轮追加时 heredoc 未正确结束，内容被吞掉，而当时我误读了测试计数为"通过"。

✓ 已补写。这是"追溯体系"的第一次实战价值：**它发现了文档与代码的不一致，而那份不一致是人工审查漏掉的。**
