# WebUI 模块设计（M15）

> 定位：**只读的系统观察窗**，不是控制台。
> 访问方式：SSH 隧道（参照 OpenViking 只监听 `127.0.0.1` 的做法）。
>
> 状态：**设计稿，未实现。** 三个决策点待定，见第 七 节。

---

## 一、先纠正三个前提

设计前核实了当前代码，有三个事实与"直觉上应该有的"不符，它们会直接改变方案。

### ① 你要的「名称」，运维接口现在**没返回**

角色卡里确实有 `display_name`（示例配置里是 `Coordinator` / `Strict Node` /
`Open Node`），但 `POST /nxs/ops/nodes` 的输出里**没有这个字段**：

```
实际返回: node_id, domain, state, approved, revision, last_seen,
          capabilities, max_response_level
```

所以"查看节点名称"这件事，**当前连数据都拿不到**，要先补接口。

### ② 你要的「简介」，角色卡里**根本没有这个字段**

`RoleCard` 的字段是：

```
card_version, node_id, display_name, domain, reachability,
heartbeat_interval, roles, capabilities, constraints
```

没有 `description`。要支持"简介"，**需要新增字段**——这是协议契约变更，不是加个 UI 就行。

### ③ `display_name` 与将来的 `description` **零校验**，且是节点自报

`display_name` 接受任意长度、任意字符：没有长度上限、没有字符过滤、
没有非空要求。它是节点**自己填**的（自注册时提交）——也就是**不可信输入**。

这意味着 WebUI 会直面的两个问题：

* **XSS**：节点把名字填成 `<img src=x onerror=...>`，UI 若不转义就中招
* **撑爆布局**：填一个 10 万字符的名字

而且还有一个更微妙的风险：**`description` 可能变成数据外泄通道**——
节点把业务内容写进自己的"简介"（"我今天处理了张三的简历"），
hub 的运维就能看到。这与"能力声明也是自报的"是同一类问题，
但"简介"是自由文本，比能力类型名危险得多。

> 这三条说明：**WebUI 不是一个纯前端任务。** 它牵动接口契约与安全边界。

## 二、形态：独立进程 `nxs ui`，不塞进现有网关

### 三个候选

| 方案 | 做法 | 问题 |
|---|---|---|
| A 塞进网关 | 网关加 `/ui` 静态路由 | ❌ 见下 |
| **B 独立进程**（推荐） | `nxs ui`，监听 `127.0.0.1`，反过来调 hub 的 ops 端点 | 多一个进程要管 |
| C 纯静态文件 | 给一个 HTML，用户自己起任意服务器 | ❌ 解决不了密钥问题 |

### 为什么不塞进网关（A 被否的理由）

网关当前的信任模型是单一且干净的：**所有请求都是 HMAC 签名的机器身份**。
它的每条代码路径都为这个模型服务（`_authenticate` → 策略 → 边界）。

塞进 WebUI 意味着同一进程里出现第二套信任模型：**带 Cookie 的浏览器**。
两者要共用端口、共用限流、共用错误处理，而它们的威胁模型完全不同：

* 网关的威胁是"某个节点被攻破，试图越权"
* WebUI 的威胁是"浏览器里的页面被注入，或者有人偷了 token"

混在一起的后果：WebUI 的漏洞（XSS、CSRF、token 泄漏）会落在
**承载所有节点流量的那个进程里**。这与本项目一贯的"拒绝到实现层"相反——
本该隔离的东西不该共享进程。

独立进程还有两个实际好处：它崩了不影响核心；它天然只监听本地。

### B 方案的形状

```
┌─────────┐  SSH 隧道   ┌──────────────────┐   看      ┌──────────────┐
│ 浏览器   │ ─────────> │ nxs ui           │ ───────> │ hub 的       │
│ (你的电脑)│  127.0.0.1 │ 127.0.0.1:8080   │  HMAC    │ /nxs/ops/*   │
└─────────┘            │ · 只读            │ 签名     │ (已有)        │
                       │ · token 鉴权      │          └──────────────┘
                       │ · 无数据库访问     │                 │
                       └──────────────────┘                 ▼
                                                    注册表 / 队列 / 指标
```

## 三、数据路径：走 ops 端点，**不直连数据库**

这是本方案最重要的一条约束。

UI 进程**不 import 任何存储后端，不读 sqlite，不碰注册表**。
它只做一件事：用运维密钥调 hub 的 `/nxs/ops/nodes` 与 `/nxs/ops/metrics`。

### 为什么这条不能妥协

如果 UI 直读 sqlite，就等于**新增了一条绕过策略层的数据通道**。
本项目的铁律是「**所有安全策略的唯一裁决处**」——策略层是唯一的，
数据出口也必须是唯一的。多开一个出口，就等于多一个没人检查的门。

走 ops 端点的好处是**能看什么完全由已存在的边界决定**：

* 节点密钥调 ops 是 403（已有保证）
* 读动作不留痕（`nodes` / `metrics` 没有 `record_ops`）——
  所以 UI 轮询**不会刷爆审计日志**（这一点已核实）
* 写动作（approve/revoke/release）才留痕

### 代价：UI 进程需要 `NXS_OPS_SECRET`

看起来像"扩大了权限面"，其实没有：

能启动 `nxs ui` 的人必须能 SSH 登录这台机器，而能 SSH 登录的人
本来就能 `export NXS_OPS_SECRET` 然后直接 curl。**UI 没有给他新能力，
只是把已有能力变好用。**

> 但这条要在部署文档里写明：**`nxs ui` 的进程环境里有运维密钥。**
> 所以它不该由 root 之外的人运行，也不该配合 `--host 0.0.0.0` 使用。

## 四、鉴权：SSH 隧道 + 一次性 token，**不做账号密码**

### 为什么不做账号密码

做账号密码意味着要引入：密码存储（哈希+salt）、改密流程、忘记密码流程、
防暴力破解、会话管理。这一整套东西的收益是……**零**。

因为 SSH 隧道已经完成了强认证。能建立隧道的人已经有 shell 权限，
给他一个"用户名密码"只是多一道他不需要的门。

### 两层设计

| 层 | 机制 | 防什么 |
|---|---|---|
| 第一层（网络） | 只监听 `127.0.0.1` | 外部直接访问（必须走 SSH 隧道） |
| 第二层（应用） | 启动时生成随机 token | **同机器上的其他用户**（他们也能连 `127.0.0.1`） |

token 的具体做法：

* 每次启动 `nxs ui` **重新生成**（不落盘，不跨重启复用）
* 打印在终端：`打开 http://127.0.0.1:8080/?t=<token>`
* 首次访问后写入 `HttpOnly; SameSite=Strict` cookie，之后靠 cookie

**为什么 token 不能只放 URL**：URL 会进浏览器历史、会被 Referer 带出去、
会被截图分享。所以它是"进门一次的钥匙"，进门后立刻换成 cookie。

**为什么不做会话过期**：进程停了 token 就失效了。这比"8 小时过期"更彻底，
也更简单——**没有持久化的会话，就没有可被窃取的持久会话**。

## 五、只读：MVP 不做任何写操作

### 理由

写操作会引入一整类新问题：CSRF 防护、操作二次确认、误操作恢复、
并发写入冲突。而这些问题的收益很低——**批准/吊销本来就是"需要人做决定"的动作**，
它更适合留在 CLI 里（那里有 shell 历史，天然形成操作记录）。

只读还有一个安全好处：**即使 UI 被 XSS，泄漏的也只是节点元数据**——
而 ops 端点本来就能拿到这些，攻击者不需要绕这么大圈。

### 代价（说清楚）

看到异常节点，要切回终端敲 `nxs ops revoke`。这是刻意保留的摩擦。

如果你觉得这个摩擦太大，见第七节的决策点 ②。

## 六、页面内容（MVP）

用户要的三样 + 我建议补的：

### 主视图：节点列表

| 列 | 来源 | 现状 |
|---|---|---|
| **名称** | `display_name` | ⚠ **需先补进 ops nodes** |
| **简介** | `description` | ⚠ **需新增字段** |
| **角色** | `roles`（issuer/executor/…） | ⚠ 需补进 ops nodes |
| 节点 ID | `node_id` | ✅ 已有 |
| 域 | `domain` | ✅ 已有 |
| 状态 | `state`（alive/stale/revoked） | ✅ 已有 |
| 已批准 | `approved` | ✅ 已有 |
| 最后心跳 | `last_seen` | ✅ 已有 |
| 能力 | `capabilities` | ✅ 已有 |
| 应答上限 | `max_response_level` | ✅ 已有 |

**视觉上最重要的是"状态"与"是否批准"** ——因为未批准的节点是无法协作的，
它是最常见的"为什么派不过去活"的原因。建议用颜色区分，而不是让人读字段。

### 副视图：系统汇总

取 `/nxs/ops/metrics`，只显示四项，不做图表：

```
提交 42 · 完成 40 · 失败 0 · 拒绝 2
延迟 p50 12ms · p95 46ms · p99 89ms（128 样本）
积压：node-a 2/8  执行中 1
```

**刻意不做**：折线图、时间序列、告警面板。
理由：这些需要存历史数据（现在是内存态、重启归零），
而 MVP 阶段"一眼看健康"比"看趋势"重要得多。
趋势属于将来接 Prometheus 之后的事。

### 刻意不做

* 任何写操作（见第五节）
* 任务详情页（涉及产出内容，那是另一个安全等级）
* 实时推送（见下）
* 登录页（token 走 URL 一次，不做表单）

### 轮询而非 SSE

每 3–5 秒拉一次 `/api/state`（UI 进程自己的聚合端点）。

不用 SSE 的三个理由：

1. SSE 会占网关的连接配额（`QT-CONN-06`），而 UI 只是本地一个人看
2. `/nxs/events` 的设计是"只推有活、不推内容"，它本来就不适合当 UI 数据源
3. 轮询在 UI 进程里聚合，实现简单且无状态

## 七、三个待你决策的点

### 决策 ① 「简介」字段怎么处理

| 选项 | 说明 | 代价 |
|---|---|---|
| **A 新增 `description`**（推荐） | 角色卡加一个可选字段，只放静态描述 | 改协议契约；要定长度上限 |
| B 从 capabilities 自动生成 | "提供 work.calendar / work.summary" | 不是"简介"，但零契约变更 |
| C 不做 | 只显示名称 | 不满足你的需求 |

选 A 的话有一个必须同时做的事：**明确它的语义是"静态描述，不得承载业务数据"**，
并在协议文档里写清楚。否则它会变成一条没人当回事的外泄通道。

### 决策 ② 只读还是带最小写操作

| 选项 | 说明 |
|---|---|
| **A 纯只读**（推荐） | 看到问题切回终端。零 CSRF 风险 |
| B 只读 + 批准/吊销 | 多两个按钮，但要引入 CSRF token、二次确认、操作审计关联 |

我倾向 A：MVP 阶段"看得见"比"点得动"重要，而且审批动作天然低频。

### 决策 ③ 端口与绑定

建议默认 `127.0.0.1:8080`，且**拒绝绑定 `0.0.0.0`**（除非显式加 `--allow-public`
并打印醒目警告）。这与网关的默认 `127.0.0.1` 一致。

如果你将来想不通过 SSH 隧道、直接从公司内网访问，那时再讨论。
但我不建议——SSH 隧道不需要额外开防火墙端口，也不需要证书。

| 编号 | 功能点 | 依赖 | 备注 |

| M15.F2 | **一次性 token 鉴权**（启动生成、打印、换 cookie） | F1 | token 不落盘、不跨重启 |
| M15.F3 | **数据经 ops 端点获取**（不 import 存储后端） | F1 | 用测试保证"UI 不碰后端" |
| M15.F4 | **节点列表视图**（名称/简介/角色/状态/能力） | F3 | 需先补 ops nodes 字段 |
| M15.F5 | **系统汇总视图**（计数 + 延迟分位数 + 积压） | F3 | 只读 metrics，不做图表 |
| M15.F6 | **自报字段安全渲染**（HTML 转义 + 长度截断） | F4 | 防 XSS 与撑爆布局 |
| M15.F7 | **`display_name` / `description` 校验**（长度上限、字符集） | — | 补在 RoleCard 解析处（服务端，不只靠前端转义） |
| M15.F8 | **只读保证**（无任何写端点；UI 进程无写权限） | F1 | 用测试保证"没有 POST 处理器" |

### 配套改动（不属于 M15，但必须一起做）

| 改动 | 位置 | 说明 |
|---|---|---|
| `ops nodes` 补字段 | `nxs/edge/gateway.py` | 加 `display_name`、`description`、`roles` |
| `RoleCard` 加 `description` | `nxs/core/models.py` | 可选字段，默认空串 |
| 协议文档更新 | `docs/protocol.md` | 写明新字段与语义约束 |
| 部署文档补一节 | `deploy/README.md` | SSH 隧道的具体命令 |

### 为什么 F7 放在服务端

**不能只靠前端转义。** 如果 `display_name` 能被填成 10 万字符，
那它在**进入注册表时**就该被拒——否则它会一直躺在那里，
将来任何消费方（不止这个 UI）都要各自防一遍。

这与 `params_schema` 那条"只声明不校验"的教训是同一条：
**校验要落在能被信任的位置**，而不是每个下游各自补。

## 九、SSH 隧道怎么用（预演）

```bash
# 在服务器上，只监听本地
nxs ui --port 8080
# 输出：打开 http://127.0.0.1:8080/?t=<token>

# 在你电脑上，建隧道
ssh -N -L 8080:127.0.0.1:8080 user@your-server

# 浏览器打开
open http://127.0.0.1:8080/?t=<token>
```

与 OpenViking 完全一致的模式：服务只听 `127.0.0.1`，靠 SSH 把端口搬过来。
**不需要**：开防火墙端口、申请证书、配 Nginx、做 HTTPS。
因为流量从不出本机，TLS 是 SSH 提供的。

> ⚠ 一个容易忽略的点：**不要把 token 粘到别的机器上**。
> token 只在你 SSH 进来的那个终端里可见，这正是它的价值。

## 十、我建议的实施顺序

分三步，每步都能独立验收：

```
第 1 步（半天）· 数据先通
  ├─ ops nodes 补 display_name / roles
  ├─ RoleCard 加 description + 校验（长度上限 200 字符）
  └─ 验收：`nxs ops nodes` 的表格能看到名称与简介
     （⚠ `nxs ops` **没有 --json**，只有表格输出。若要 JSON，
     第 1 步顺带给它加一个 `--json`，或直接用 curl 调 ops 端点）

第 2 步（一天）· UI 能用
  ├─ nxs ui：只读进程 + token + 单页
  ├─ 节点列表 + 系统汇总
  └─ 验收：SSH 隧道打开，能看到所有节点

第 3 步（半天）· 守住边界
  ├─ 测试：UI 不 import 存储后端 / 没有 POST 处理器 / 拒绝 0.0.0.0
  ├─ 测试：超长与含标签的 display_name 被拒
  └─ 验收：注入腐化 → 测试变红
```

**第 1 步就是最小可交付**：即使 UI 还没写，`nxs ops nodes`
也已经能在终端看到名称和简介了——你现在就能用。

> 顺带说明：`nxs ops` 目前只有表格输出，没有 `--json`。
> 这是第 1 步可以顺手补的（`nxs metrics` 已经有了，不一致）。

## 十一、这个模块不做什么（避免范围蔓延）

| 不做 | 原因 |
|---|---|
| 任务详情与产出内容 | 产出是另一个安全等级，且有 186 KB 上限问题 |
| 登录页 / 多用户 / 权限分级 | 单人运维场景，SSH + token 已足够 |
| 图表与时间序列 | 指标是内存态、重启归零，画不出有意义的趋势 |
| 写操作（MVP 阶段） | 见第三节 |
| HTTPS | SSH 隧道已提供传输加密 |
| 实时推送 | 轮询更简单，且不占网关配额 |
| 移动端适配 | 面向运维终端，不做响应式 |
