## 00方法论：我认同什么，补什么

### 0.1 你的思路成立

> **我认同核心判断，而且认为它是这个规模的项目下唯一可行的路径。**

代码量已超出人工阅读极限（核心 4.7k 行 + 测试 1.9k 行）。既然读不完，
就必须换一个能**证伪**的检验方式——而"代码是否实现了设计"比"代码写得漂不漂亮"
更接近本质，因为**代码的价值完全由它实现的功能决定**。

**而且这条路有个额外好处：它把"信任"从"我读过代码"转移到"可复现的证据"上。**
你不需要相信我的判断，你只需要看需求清单是否完整、以及测试能否真的证伪。

### 0.2 但有三处盲区，必须补上

盲区一：测试只能验证"被想到的东西"

测试无法证明"某个要求被遗漏了"。如果设计里少了一条安全约束、或者我对某个要求的
 理解本身就错了，**测试会忠实地验证那个错误的理解，然后全绿**。

 更隐蔽的是**同源问题**：设计文档与测试出自我同一双手。同一个误解会同时写进
 设计和测试，于是测试通过反而加强了错误结论。

→ 对策：本文件把需求从设计文档里**逐条抽出、独立编号**（见 01 节），请你**先审这份清单本身**——包括"有没有该有但没有的"。这一步不能由我代劳。

盲区二：测试验证"行为"，无法验证"不存在的行为"

"不该给的数据在实现层不存在代码路径"这类要求，正向测试**永远证明不了**——
 你只能证明"我试过的路径都被拒了"，不能证明"没有其他路径"。

 所以本文件引入了**结构性检查**（静态扫描源码，而非运行行为），
 覆盖了一部分。但它的完备性同样无法自证。

→ 对策：对这类要求改用**对抗性验证**——主动尝试绕过并展示失败（见 05 节）。它比正向测试强，但仍不是证明。

盲区三：设计文档本身可能是错的

"实现是否符合设计"只保证**内部一致性**，不保证设计符合真实需求。
 一份自洽但与现实脱节的设计，加上忠实实现它的代码，会得到一套完美的错东西。

→ 对策：这一层只能靠你。所以 01 节把需求写成**可判定的断言**而不是散文——便于你逐条判断"这条要求本身对不对"。

> **因此本文件的分工是：**

> - **我负责**：把需求抽全、把实现与验证对上、把验证强度如实标注、把缺口挖出来
> - **你负责**：审"需求清单本身"——有没有缺的、有没有不该有的、有没有表述含混的

> **审完 01 节再往下看 02/03 才有意义**——因为后面全是基于这份清单的对照。

## 03验证强度分布

这是本轮审查**最重要的结论**——它回答"测试是否真的满足要求"，而不只是"有没有测试"。

### 3.1 五级证据强度定义（仅声明–对抗）

> **为什么这套尺度不占用字母？**

本项目里 `L` 曾同时表示两件事：**数据等级**与**验证强度**。
后果是——读到"L1"时无法确定它指"摘要级数据"还是"静态检查强度的测试"。

数据等级已改用语义名（`metadata` / `summary` /
`fragment` / `full_text`），
而本文件的强度标记**直接使用词**（对抗 / 端到端 / 单元 / 静态 / 仅声明），
不再缩写为字母 —— 因为它只在本文档内用于评估，
不是一个会被跨文档引用的实体标识。**给空闲字母派用途，正是本次要避免的错误。**
详见 `CONTRIBUTING.md` 的「编号体系总览」与 C8。

| 级别 | 含义 | 说明 |
|---|---|---|
| 对抗 | **主动尝试绕过并失败** | 最强的证据形式。不是"我测了它会拒"，而是"我试过绕过，绕不过" |
| 端到端 | 完整链路上的行为验证 | 投递 → 领取 → 执行 → 边界 → 回传 → 审计，全流程参与 |
| 单元 | 模块级行为验证 | 只验证单个模块，模块间协作靠 端到端 覆盖 |
| 静态 | 代码/配置层的结构性断言 | 不运行行为，只扫描源码或断言配置。能覆盖"不该存在的东西" |
| 仅声明 | **文档写了，机器无验证** | 最弱。靠"没写这块代码"证明，无法防止将来误加 |

> **结论一：P0 的 10 条安全要求**全部**达到 单元 以上，其中 **4 条达端到端**。**

这是最有意义的一点——**系统"存在的理由"那部分，验证是扎实的，没有一条停在「仅声明／静态」**。
四条 端到端 里含**三条安全断言**（类型白名单 S1 / 应答边界 S2 / 跨域拒绝 S3）
与**人工批准 S9**，它们都在 demo 里可复现，不依赖单元测试的自证。

（本文件早先手工统计有误——单元/静态 两处数字写错，P0 的 端到端 条数也少算一条。 已改为**用脚本从表格实测**，不再靠人工数。这也是一次自身的"同源问题"实例： 手工统计与手工编写的表格容易互相印证错误。）

> **结论二：对抗性验证为 0——这是本报告最大的诚实交代。**

现有的三条 端到端 断言，验的是"**常规路径**被拒绝"。它们**没有回答**：

> - 类型名里塞特殊字符（demo.echo; drop）会怎样？
> - 字段用超深嵌套或列表套列表绕过白名单检查会怎样？
> - 伪造 from_node 后签名还来得及拦吗？
> - 用同一 session 复用一次跨域授权，能否扩大范围？

> **这些是"攻击者会做的事"，而当前测试全部是"正常用户会做的事"。**
见 05 节的对策。

> **结论三：仅声明 只剩 3 条，且本轮已把 4 条从 仅声明 提升到 静态。**

审查开始时 仅声明 有 6 条，全部是 P3「不做」类。它们的失效方式完全相同——
**有人无意中引入一个依赖**，而这没有任何测试会拦住。

已用一个廉价的测试同时守护其中四条（**N1 / N5 / N6 / N7**）：
断言 pyproject.toml 的运行时依赖**恰好只有 PyYAML**，

剩下 3 条 仅声明（N3 / N4 / N8）本质是"**不存在的代码路径**"，
机器无法证明——只能靠代码审查与设计评审。

## 04审查发现（6 项）

本轮审查过程中实际挖出的问题，按严重性排序。**前两项是我主动发现并已修的**——它们都不在你提的两个维度里，属于"读文档核对实现"时掉出来的。

已修 ① TLS 配置完全无效，但输出显示 [TLS]

**现象**：describe 会根据 tls_cert 是否配置打印 [TLS] 或 [明文]，看起来像是 TLS 状态指示。但实际上——**没有任何一行代码用 tls_cert/tls_key 去启用 TLS**（v0.1 根本没有 HTTP 传输层）。tls_key 更是连显示都没用上。

 **为什么比"缺字段"更糟**：缺字段会报错。**而这里输出主动声称了一项并不存在的防护**——运维看到 [TLS] 会以为链路已加密。这是**主动误导**，不是消极遗漏。

 **同类问题还有一处**：describe 曾打印"速率上限 20/秒/节点"，而速率限制同样未实现。

✓ 修法：describe 不再声称未实现的功能；改为在末尾列出**已知未实现项**（机器可读的 config.UNIMPLEMENTED 清单驱动）。现在 nxs verify 会明确打印这 5 项。

已修 ② 死配置字段：allow_issue

**现象**：MatrixRule.allow_issue 被定义、被解析、被写进示例配置——**但从未被任何逻辑读取**。

 **危险点**：它完全静默。配置校验通过、demo 跑通、测试全绿，而配了它的人以为自己获得了某种控制。

✓ 修法：删除字段 + 三处配置引用；新增 CONTRIBUTING 第六条纪律「配置字段必须被使用」；新增 TestConfigFieldsAreUsed(3) 自动守护。

已文档化 ③ 四个配置项被静默接受（功能未实现）

用新写的字段扫描测试一扫，又掉出来 4 个同类问题：

| 配置项 | 缺什么 |
|---|---|
| rate_limit_per_second | 速率限制器未实现 → **限流不生效** |
| params_schema | 参数校验未实现 → **格式错误的参数会被投递出去** |
| bytes_per_day | 响应字节数未按节点累计 → **按日字节配额永不触发** |
| max_body_bytes | 传输层未实现 → 上限无处施加 |

**注意 params_schema 这一项**：角色卡声明了参数格式，但没有校验。
 这意味着一个类型正确、格式错误的请求会被投递出去，由执行节点自己承担失败——
 **失败点被推到了更远的地方，排查成本更高**。

→ 处理：不静默实现（那会模糊本次审查的边界），而是**显式文档化**——写入 config.UNIMPLEMENTED + describe 输出 + docs/architecture.md「已知缺口」一节，并加测试确保三者一致。**是否在 v0.2 补齐由你决定。**

已修 ④ 测试盲区导致的真 bug：凭据环境变量路径从未被验证

**现象**：我在重构 load_config 时，误删了 env 的归一化赋值，导致**不传 env 参数时会崩溃**（AttributeError）。

 **为什么全套测试没发现**：所有既有测试都显式传 env=demo_env，
 于是"**从 os.environ 读凭据**"这条**真实部署唯一使用的路径**从未被覆盖。
 测试全绿，而生产路径是坏的。

 **这是盲区一（同源）的具体实例**——测试和实现共享同一个"测试会传 env"的隐含假设。

✓ 修法：修 bug + 新增 TestConfigFromEnvironment(3)：不传 env 时从 os.environ 读取 · 缺失时正确报错 · 凭据类型为 bytes。

已澄清 ⑤ boundary.py 的定位与设计原则冲突

**现象**：设计原则写明"Nexus 不做内容层面的安全判断"（注入检测、脱敏属于节点侧）。
 但 nxs/data/boundary.py 确实做了内容处理——剥离指令性前缀、去控制字符、字节截断。

 它就在 nxs/ 包里，而设计文档的 D1–D4 模块列表里**根本没有"应答边界"这个模块**。

→ 处理：定位不冲突，但需要说清——**boundary.py 语义上属于节点侧组件**（应部署在节点上），只是为让 demo 能在单进程内验证完整链路才放在同一仓库。已写入 docs/architecture.md。 → **建议的整理方向**：拆成独立的节点侧包（如 sdk/boundary），让"哪些代码该部署在哪里"一目了然。这是 v0.2 的结构调整，不在本轮做。

待修 ⑥ 两套模块编号冲突，会让读者困惑

**现象**：《v0.1 MVP 规划》用 M1–M8 给八个待开发项编号；
 而《系统定义》用 M1–M4 给**管理面的四个模块**编号。两套含义不同：

| 编号 | 在《v0.1 规划》里 | 在《系统定义》里 |
|---|---|---|
| M1 | 配置中心 | 配置中心（巧合一致） |
| M2 | 注册中心 | **审计留痕**（冲突） |
| M5–M8 | 策略 / 边界 / 网关 / 审计 | **不存在** |

**根因**：规划文档里的 M 其实是"**任务**编号"（Milestone 或 Module 待开发项），
 不是模块编号——但与模块编号用了同一个前缀。

→ 建议修法：把《v0.1 规划》的 M1–M8 改为 T1–T8（Task），与模块编号彻底分开。本轮未改，等你确认命名偏好。
