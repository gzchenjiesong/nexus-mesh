### 0.2 我的判断：不必改系统名，但仓库名建议调整

> **先说结论：这不是强竞争者，不构成你放弃的理由。**

星数 0、3 天停更、作者其他仓库不严肃——这是一个**个人概念验证**，不是在做产品。它对你的实际威胁只有一条：**占用了 PyPI 的名字，且它的描述与你的高度相似**，将来别人搜索时可能混淆。

**而且它的存在对你有正面价值**：说明这个方向确实有人在独立想到，你的判断不是孤例。它的 nexus hub + worker/orchestrator + 能力发现的设计，与我们的架构**方向一致**——你可以拿它当一个粗糙的参考实现看（3 天工作量，参考价值有限，但可以看看它公开了哪些接口设计）。

> **一个我认为更重要的差异：你们的目标根本不同。**

> |  | 它 | Nexus Mesh（你的） |
> |---|---|---|
> | **野心** | 做「通用标准」——"universal protocol"、"RFC-001 compliant"、跨语言、联邦 | **解决自己的跨环境协作问题**——三个异构 Agent、跨信任域、数据安全约束 |
> | **核心难点** | 协议完备性与兼容性 | **权限矩阵与应答边界**——"让被攻破的 Hub 拿不到原始数据" |
> | **复杂度来源** | 跨语言 SDK、联邦、标准化 | 跨信任域的数据分级、离线恢复、异构宿主 |

> **所以你不必与它争"协议标准"这个位置。**把"为自己的真实约束解决问题"做扎实，比做一个没人用的通用标准有价值得多——**而这恰好是你已经在做的事**（那个 0 星项目和你的文档深度不是一个量级）。

### 0.3 命名调整建议

✓ 我的建议：系统名 Nexus 保留，仓库名与发布名用 nxs-mesh

| 层次 | 建议 | 理由 |
|---|---|---|
| **系统名** | **Nexus** 不变 | 这是内部系统名，且你选它的理由（"思想连接"）成立。**不发布就不冲突。** |
| **工程名 / 仓库名** | **nxs-mesh** 建议调整 | nexus-mesh 在 GitHub 有 5 个同名 + PyPI 被占；**nxs-mesh 在三个生态全部唯一**（GitHub 0 同名、PyPI 可用、npm 可用） |

| **import 模块名** | nxs 完全可用 | **模块名是本地概念，不受 PyPI 占用影响。**你定的代号 nxs 在代码里照用 |

> **一句话总结这次调整：nxs 这个代号完全不受影响（代码里照用）；需要变的只是**对外可见的仓库名与包名**，从 nexus-mesh 改为 nxs-mesh。**

如果你觉得 nxs-mesh 不好看，另一个可选是 nexusmesh（连写）——它也可用，但 GitHub 上有 12 个同名仓库，辨识度不如 nxs-mesh。

## 03 v0.1 功能列表

范围原则：**只做能跑通一个完整闭环的最小集合，并且每一项都必须验证一个设计假设。**凡是"以后加不会更贵"的，一律推到 v0.2。

### 3.1 v0.1 必须完成（8 项）

| # | 模块 | 做什么 | 验证的假设 |
|---|---|---|---|
| **M1** | **配置中心**<br>nxs/mgmt/config | 从 YAML 加载：成员名单、权限矩阵（域 × 类型）、任务类型注册表（含字段白名单）、配额。启动时校验配置合法性 | **配置化而非代码化**——加成员、加任务类型只改配置 |
| **M2** | **成员注册与心跳**<br>nxs/control/registry | 提交角色卡（角色 / 能力 / 约束）；心跳维护 last_seen；存活三档 alive / stale / revoked；**首次注册需人工批准** | 能力声明能否成为唯一权威；**加成员是否需要改代码**（这是"独立基础设施"的判据） |
| **M3** | **信箱与投递**<br>nxs/data/mailbox | 任务投递、拉取（**拉取即加锁**）、空队列返回 204、不做长轮询 | Egress-Only 下的"信箱式投递"能否替代 RPC |
| **M4** | **任务生命周期与租约**<br>nxs/data/task | 状态机（submitted → working → completed / failed / canceled，含 input_required）；**租约超时自动释放**；幂等键去重；最大重试次数 | **断电恢复零人工干预**——这是你明确要求的 |
| **M5** | **策略执行点**<br>nxs/control/policy | 权限矩阵校验（**默认拒绝**）；任务类型白名单；域间可达性；配额与速率限制；**拒绝时只返回 rule_id** | **权限能否挡住越权**——安全设计的第一道验证 |
| **M6** | **应答边界**<br>nxs/data/boundary | 按角色卡的 response_fields 过滤字段；**等级上限硬约束**（片段级 / 原文级 成员侧不存在代码路径）；semantics=data 强制标注；越界即拒绝并本地告警 | **"被攻破的 Hub 拿不到原始数据"**——这是整个系统存在的理由 |
| **M7** | **网关与认证**<br>nxs/edge/gateway | TLS 终止；**HMAC-SHA256 请求签名**（时间戳 + nonce 防重放）；每成员独立凭据；请求体大小限制 | 轻量认证是否够用（mTLS 是否必须） |
| **M8** | **审计留痕**<br>nxs/mgmt/audit | 每次协作记录元数据：时间 / session / task_id / type / from / to / 命中规则 / 应答等级 / 字节数 / 结果。**只记元数据不记业务内容**；写入失败熔断 | 可追溯性；**审计能否不成为数据集中点** |

### 3.2 配套交付（让 MVP 真的能跑）

#### 成员 SDK（最小）

让一个 Agent 能接入的客户端库：**注册 / 心跳 / 轮询 / 执行回调 / 回传**五件事。**不含任何业务逻辑**——它是接入用的骨架，不是框架。

#### 两个 demo 成员

一个 member-a（上限为摘要级、模仿最严约束）、一个 member-b（上限为片段级）。**用中性名字与中性任务**，不含任何真实场景。

#### 一键 Demo 脚本

一条命令跑出完整协作流程并打印每一步。**这是 README 第一屏要展示的东西**——别人 clone 下来 30 秒能看到效果。

#### Dockerfile + compose

直接体现"迁移只是重新部署"。**也让你自己在不同机器上验证迁移路径。**

#### 测试

覆盖四条安全断言：**① 未注册类型被拒 ② 越界字段被拒 ③ 跨域委托被拒 ④ 租约超时后任务可被重新领取**。这四条是 v0.1 的核心测试。

#### 文档（脱敏版）

README.md · docs/architecture.md · docs/protocol.md。从现有系统定义文档裁剪而来（见 01.2）。

### 3.3 v0.1 明确不做（推迟到 v0.2+）

| 不做 | 为什么可以推迟 | 推迟到 |

## 04 验收标准（Demo）

v0.1 是否完成，不看写了多少代码，**看下面这七步能否在一条命令里跑出来**。

```
$ make demo     # 或 docker compose up demo

[1/7] 启动 Nexus 核心 .................. OK  端口 8443 · 配置 nxs.yaml
[2/7] 两个成员注册
       member-a  domain=zone-a  level≤summary  caps=[demo.echo, demo.count]   OK
       member-b  domain=zone-b  level≤fragment  caps=[demo.echo, demo.search]  OK

[3/7] 正常任务：调用 member-a/demo.echo
       → submitted → working → completed                              OK
       返回: {"echo": "hello", "level": "metadata"}

[4/7] 安全断言 ① 下发未注册类型 demo.unknown 给 member-a
       → REJECTED  rule_id=WL-TYPE-404  （不进入任何执行逻辑）      OK

[5/7] 安全断言 ② 请求 member-a 返回超出字段白名单的内容
       → REJECTED  rule_id=WL-FIELD-001（Hub 仅收到 rule_id，无内容）  OK

[6/7] 安全断言 ③ member-a 尝试发布任务给 member-b（跨域）
       → REJECTED  rule_id=MX-DOMAIN-02（默认拒绝）                OK

[7/7] 断电恢复 强制 kill member-a 进程（模拟断电）
       → 租约 15s 后超时 → 任务自动回到队列
       → 重启 member-a → 自动接续（无需人工干预）→ completed        OK

审计摘要
  session=ses-xxxx  任务 5 条  完成 2  拒绝 3  平均延迟 12ms
  拒绝原因分布: WL-TYPE-404 ×1 | WL-FIELD-001 ×1 | MX-DOMAIN-02 ×1
  全链路留痕已写入 .nxs/audit/2026-10-07.ndjson
```

> **这七步的设计意图：**第 3 步证明"能工作"；**第 4、5、6 步是三条安全断言**，它们才是这个项目区别于普通消息队列的地方；第 7 步证明断电可自愈。

**如果第 4/5/6 步有任何一条不能稳定复现地通过，v0.1 就不算完成**——因为那意味着设计里最关键的部分（权限矩阵 + 应答边界）没有被验证。

## 06 技术选型建议

### 6.1 语言对比（这个决定需要你拍板）

| 维度 | Python | Go |
|---|---|---|
| **你的熟悉度** | 高 你的其他项目都是 Python | 待确认 你的技术栈里目前没有 |
| **开发速度** | 快 表达力强，适合把逻辑想清楚 | 中等，样板代码多一些 |
| **部署** | 需要 Python 运行时（或容器） | 单二进制 无运行时依赖，拷贝即用 |
| **与"迁移只是重新部署"的契合** | 靠容器解决，效果相当 | 天然契合 一个文件搬到新机即可 |
| **并发模型** | asyncio，够用 | goroutine 更适合消息流转类负载 |
| **类型安全** | 需要额外工具（mypy） | 原生强类型 对协议类项目是加分 |
| **依赖体量** | 标准库 + 少量依赖即可 | 标准库极全 HTTP/TLS/JSON/SQLite 全内置 |
| **对社区的门槛** | 低 贡献者最多 | 中等 |

> **我的倾向：如果这是一次学习机会，选 Go；如果目标是"最快跑通 MVP"，选 Python。但有一个更实际的考量**：这个系统的核心是"消息流转 + 状态机 + 严格校验"，**Go 的原生强类型 + 标准库完备 + 单二进制部署**，与这个项目的性质确实很搭。而且它正好呼应你反复强调的"独立基础设施应该能整体搬迁"。

**不过 Python 有一个不可忽视的优势**：你的工作 Agent 侧用的是 WorkBuddy 体系，如果需要在那里运行成员客户端，Python 脚本的接入成本最低。

**如果你时间紧、想最快看到 v0.1 跑起来 —— 选 Python。如果想借这个项目把 Go 学起来，且不急于几周内出 MVP —— 选 Go。**

### 6.2 若选 Python，我的依赖建议（最小化）

| 用途 | 建议 | 说明 |
|---|---|---|
| HTTP 服务 | FastAPI + uvicorn，或 Flask | 你的其他项目用的是 Flask。**Flask 更简单，FastAPI 的类型校验对本项目更有用** |
| 数据校验 | pydantic | 信封与角色卡的 schema 校验。这是本项目的核心，值得引入 |
| 存储 | 标准库 sqlite3 | **不引入 ORM。**SQL 直接写，量级很小 |
| 配置 | PyYAML | 配置与权限矩阵用 YAML 更好读 |
| HTTP 客户端 | httpx | SDK 侧用 |
| 测试 | pytest | — |

> **依赖总数控制在 6 个以内。**这是基础设施，不是应用。**每多一个依赖，就多一个许可证要检查、多一个升级负担。**（等你定了语言，我会把这几个依赖的许可证逐一列出，确认与项目许可证兼容。）

### 6.3 若选 Go，依赖更少

> 标准库即可覆盖大部分：net/http（服务）、crypto/tls、crypto/hmac、encoding/json、database/sql + modernc.org/sqlite（**纯 Go 实现，无 CGO**，比 mattn/go-sqlite3 更适合"单二进制"诉求）。
配置用 gopkg.in/yaml.v3。**总依赖数可以压到 2–3 个。**

## 07 实施顺序

建议的顺序是**先让"拒绝"生效，再让"执行"生效**。理由：安全断言（第 4/5/6 步）是这个项目的价值所在，如果先做完执行链路再补安全，很容易把安全做成"事后拦截"而非"结构上不可达"——**这正是我们在设计阶段反复强调要避免的**。

| 步骤 | 做什么 | 可独立验收的标准 |
|---|---|---|
| **1** | 仓库骨架 + 配置中心 M1 + 信封模型 | 配置能加载并校验；信封能序列化/反序列化 |
| **2** | 注册中心 M2 + 网关 M7 | 成员能注册、心跳、被标记 stale；未签名的请求被拒 |
| **3** | **策略执行点 M5（先做拒绝）** | **未注册类型、跨域委托、越权等级——三类请求全部被拒**（此时还没有执行路径，正好证明"拒绝先于执行"） |
| **4** | 信箱 M3 + 生命周期 M4 | 任务能投递、被拉取、完成；租约超时能释放 |
| **5** | **应答边界 M6** | **返回越界字段时被拒，且 Hub 侧收不到任何内容** |
| **6** | 审计 M8 + SDK + demo 成员 | 能跑出完整的 7 步 demo |
| **7** | 脱敏文档 + README + 许可 + Docker | 按 [01 节](#s1)清单逐项核对通过 |
| **8** | 推送 GitHub | 新机器 clone 后一条命令能跑出 demo |
