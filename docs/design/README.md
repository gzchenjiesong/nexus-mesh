# 设计文档

> **本目录是需求的源头。** 代码是它的派生物 —— 改变系统应当从这里开始，而不是从改代码开始。

---

## 为什么设计文档要进版本控制

这个项目的开发方式决定了文档的特殊地位：

```
设计文档（G/M/R）  ──►  代码  ──►  测试
   ↑                                    │
   └──────────  追溯体系校验一致性  ◄────┘
```

代码由语言模型按这里的需求生成，所以**文档不是代码的说明书，文档是代码的来源**。
由此推出两条纪律：

1. **文档不进版本控制，可维护性就无从谈起** —— 无法回答"这段代码是哪一版需求生成的"
2. **文档与代码不一致时，以文档为准并修代码** —— 反过来做等于让派生物定义源头

## 文档与代码如何绑定

单靠"放进仓库"不足以保证一致性。真正起作用的是这套**可执行**机制：

| 环节 | 位置 | 作用 |
|---|---|---|
| 编号清单 | [`traceability/registry.py`](../../traceability/registry.py) | **唯一真相源**。G/M/F/R/C/N/S 全部定义于此 |
| 功能点清单 | 同上 | 51 个功能点 + 15 条模块需求，每条标注实现位置与优先级 |
| 测试声明 | `tests/test_*.py` 的 `@covers("M5.F1")` | 每个测试声明它验证哪个编号 |
| 元测试 | [`tests/test_traceability.py`](../../tests/test_traceability.py) | 校验上述三者一致 |
| 追溯矩阵 | [`traceability/MATRIX.md`](../../traceability/MATRIX.md) | 由元测试**自动生成**，勿手工编辑 |

元测试会拦住这几种不一致：

- 有功能点没有任何测试覆盖
- 测试挂了不存在的编号（改编号名后留下的死引用）
- 有测试没有声明它验证什么
- `realized_by` 指向了不存在的功能点

### 改需求的正确流程

```
① 改 docs/design/ 里的设计文档
② 改 traceability/registry.py（增删改编号与实现位置）
③ 改代码实现
④ 给测试加/改 @covers
⑤ 跑 pytest —— 元测试会告诉你哪一处漏了
⑥ 追溯矩阵自动更新
```

**②是容易被跳过的一步**，而它恰恰是让"文档—代码—测试"三者不脱节的枢纽。

## 这份文档目录的边界

**放这里**：描述"这个系统是什么、由哪些模块构成、对外契约是什么、需求如何被验证"。

**不放这里**：具体部署方的场景描述、私有配置、真实任务类型清单。
判定标准是 —— 它描述的是**这个系统是什么**，还是**某个部署方拿它做什么**？
前者是产品的一部分，后者属于部署方的私有信息。
