> 「角色模型」「三重约束」两节需要按本文重写。

## 1. 这份模型要解决什么

原设计把「权限」拆成由每个节点自己组合的一堆字段：
`roles.{issuer,executor,relay,observer,human_interface}` +
`capabilities[]` + `constraints.{can_issue_types,can_receive_from,quota}`。

实测暴露了三个后果：

| 现象 | 根因 |
|---|---|
| 5 个角色标志里 **4 个不参与任何放行判断** | 标志是凭空设想的，没有对应的判定逻辑 |
| 同名任务类型可以由两个节点声明**两套契约**，系统不报错 | 类型不是全局定义，是从卡片汇总出来的 |
| 某"内网执行者"被批准了 `can_issue_types: ["agent.ask"]`，实际**能主动给云端派任务** | 权限逐项堆叠，堆上去没人回头看整体 |

**结论：权限不该由节点逐项拼装，而应从一组预设的能力组合里选择。**

选择之后，审批只需回答一个问题：**允许这个 Agent 以这个角色加入这个域吗。**

## 2. 四层定义与归属

| 层 | 内容 | 定义方 | 变更影响 |
|---|---|---|---|
| **TaskType** 任务类型 | 交付模式 · `params_schema` · `response_fields` · 应答等级 | 运维（`local.yaml`） | 改协议，全网生效 |
| **Role** 角色 | 可否发布 · 可否广播 · 可服务哪些类型 · 应答上限 | 运维（`local.yaml`） | 改权限组合 |
| **Domain** 域 | 域清单 + 域间可达矩阵 | 运维（`local.yaml`） | 改数据围栏 |
| **AgentCard** 身份 | `id` · `display_name` · `description` · `role` · `domain` · `self_limits` · `state` | **节点自报** | 除 `role`/`domain` 外无需重批 |

### 关键区分：谁定，决定它能不能被强制

| 类别 | 定义方 | Mesh 能否强制 | 举例 |
|---|---|---|---|
| 网络侧规则 | 运维 | ✅ 强制 | 角色可否发布、域矩阵、应答边界 |
| 节点侧自律 | 节点 | ❌ 只记录 + 留痕 | 用哪些工具、工作目录、自限额 |

**这是分工，不是缺陷。** 节点申报「我能跑 Bash」是它在声明自己愿意提供什么，
不是向网络申请许可。命令在它本机执行，Mesh 看不见也管不了。

但——**必须写明它是自律，否则会被误当成硬约束**。

## 3. 角色集

只有三个。**角色数量少是这套模型的前提**，一旦超过 5 个就该重新审视分类。

| 角色 | 可发布 | 可广播 | 可执行 | 用途 |
|---|---|---|---|---|
| `worker` | ✗ | ✗ | ✓ | 只执行，不派活 |
| `driver` | ✓ | 由 flag | ✓ | 既派活也干活 |
| `publisher` | ✓ | 由 flag | ✗ | 只派活（通知源、CI 触发器等） |

### `may_broadcast` 是独立 flag，不是角色属性

广播能触达全网，威力比单播大一个量级。做成独立 flag 后：

- 审批时能明确区分「一个普通 driver」和「一个被批准广播的 driver」
- 不必为“能广播的 driver”再造一个角色

### 刻意**不定义**的两个角色

**`observer`（只读观察者）**

语义上说得通，但实现上走不通：看板需要的是**全量节点列表 + 指标**，
而这两样属于 ops 作用域。节点协议有意不提供全量映射
（不暴露"谁在提供什么"）。

给 observer 开这条通道会破坏「ops 数据是特殊的」这条原则；
不开则看板失效。且 `UNIMPLEMENTED` 里已有
「observer 没有只读订阅通道」——现在定义它等于把坑挖深。

**等真出现「节点之间互相订阅」的需求（不是「人要看看板」）再加。**

**`coordinator`（协调者）**

它在旧模型里的三个职责，新模型下各有归属：

| 旧职责 | 新归属 |
|---|---|
| 发布任务 | driver 基础发布权 + `may_broadcast` flag |
| 信息汇总（`work.summary`） | **无生产调用方**，见 §8 |
| 人机入口 | webui 走 ops 通道，不是节点 |

剩下的就是「一个能发广播的 driver」——用 flag 表达即可，造角色是多余配置。

## 4. 域：数据围栏，不是通信分区

**domain 回答的问题是「这批数据能被谁触达」，不是「消息在哪个范围广播」。**

这条定义必须写死，否则它会被当成传统网络概念而被删掉（本设计过程中
就发生过一次：先判为"通信概念、可删"，后来又因"数据暴露围栏"必须保留）。

典型划分：

| 域 | 内容 | 准入要求 |
|---|---|---|
| `work` | 公司内网数据 | 严格——进这个域的 driver 需谨慎审批 |
| `invest` | 投资相关 | 中 |
| `common` | 公共 / 无敏感数据 | 默认 |

**不允许无域。** 每个 Agent 必须显式选一个域，默认 `common`。
允许「无域」会造出第四种状态，且没有任何好处。

### 域矩阵只表达可达性，不列类型

```
(cloud, work, allowed=true)      # 不再有 allow_types / max_level
```

**代价（必须写清）**：被批准进 `cloud` 的 driver 可以向工作域发**任意类型**的任务。

控制面从「域 × 类型」两级收成「域 + 角色」两级——**仍然是两条独立约束，
只是换了维度**：域管数据围栏，角色管类型权限。

### 广播按域逐域展开

广播不能无视围栏。正确语义：

> 广播发给**所有**满足以下条件的节点：
> ① 其域被矩阵允许从发起方域到达
> ② 其角色可服务该类型
> ③ `state == available`

否则一个公共域的 driver 发广播，工作域机器被波及，围栏就白设了。

## 5. 投递判定链

```
① 发起方 role 允许发布？
      否 → MX-ISSUER-01
② 若交付模式为广播：该实例有 may_broadcast？
      否 → MX-ISSUER-01
③ 按交付模式展开目标集合：
      unicast   → to_node 指定的那一个
      broadcast → 见 §4「广播按域逐域展开」
④ 逐目标校验：
      目标域对发起方域可达？   否 → MX-DOMAIN-02
      目标 role 可服务该类型？  否 → WL-TYPE-404
      目标 state == available？ 否 → 跳过（广播）/ 报错（单播）
⑤ 应答上限 = min(role.max_response_level, agent.self_limits.max_response_level)
```

**就低原则保留。** 多重独立来源、每一方只能收紧不能放宽 ——
这是防止单点配错导致越界的唯一保障。只是从三重变两重。

删掉的检查（多余设计）：

- ~~按 `can_issue_types` 逐类型比对~~ → 角色整体决定能否发布
- ~~按 `can_receive_from` 逐来源比对~~ → 域矩阵承担
- ~~`providers_of` / `registered_types` 按类型路由~~ → 类型全局定义后天然唯一

## 6. 状态与自限

### 三种状态，两种来源

| 状态 | 谁决定 | 含义 |
|---|---|---|
| `available` | 节点 | 正常接单 |
| `paused` | **节点主动申报** | 我活着，但暂时不接单（额度耗尽、维护） |
| `stale` | **Mesh 观测** | 心跳超时，可能已死 |

### paused 的传导机制

配额是节点自己的事，与角色无关、与 Mesh 无关。正确传导：

```
Agent 发现额度耗尽
  → 主动拒绝后续执行
  → 向 Mesh 申报 state=paused（带 reason + 可选 until）
  → Mesh 不再给它发广播/多播
  → 其他 Agent 从 nxs nodes 看到 paused，不再发单播
  → 额度恢复，节点自己 resume
```

**恢复由节点自己发起**，不由 Mesh 按时间自动恢复。

理由：`until` 是节点对未来的猜测，猜错（额度提前恢复、或机器关机）
都会让状态与事实脱节。**只有节点自己知道现在能不能干活。**

崩在 `paused` 状态也不会卡死：心跳停了，Mesh 判 `stale` 接管。

### 排队 vs 限制：两者的边界

**信箱是排队机制，任务按顺序执行。不设并发硬上限。**

- 删除 `QT-CONC-05`（并发超额拒绝）、`QT-TASK-01`、`QT-BYTE-02/03`
- 交付**总是成功**，慢消费者只是积压 `pending`
- 是否要限、限多少，是节点自己的防御机制（通过 `paused` 表达）

**但有两件事必须保留**，它们不是节点配额，是 **Mesh 自我保护**：

| 保留 | 原因 |
|---|---|
| `QT-RATE-04` 请求速率 | 防止单个节点打爆网关 |
| `QT-CONN-06` 连接数 | 防止耗尽文件描述符 |

区别在于：前者是「你还能不能干活」，后者是「网络会不会被你拖垮」。
后者必须由 Mesh 强制。

**`capacity` 的残留用途**：不再用于限制，但自动匹配排序仍需要它算
负载率（`load_ratio = pending / capacity`）——绝对数量会冤枉高并发
节点。建议保留为 AgentCard 的可选字段，**语义降级为「排程提示」**，
不再是配额。

### 队列深度上限：`max_backlog` 缺省 **20**

**为什么是必填且有默认值**：不设上限意味着积压可以无限增长，
发布方会以为自己投递成功，而节点可能已经压了几百个。
节点唯一的防御是主动说 `paused`，但它可能还没意识到就被淹了。

用生产数据估量级（`work.query` 延迟 p50 ≈ 1.8 分钟，样本仅 9 个）：

```
深度 20  →  最坏等待 ≈ 36 分钟
深度 50  →  最坏等待 ≈ 90 分钟
```

36 分钟对"派个任务让内网查点东西"可接受；再长，发布方不如换节点。

**缺省值定为 20，不是 `None`（不限）。** 理由：留一个"不限"的默认，
等于让所有人默认不受保护，且这个默认很容易被忘记。20 是保守的起点，
节点要放宽就显式写大——**保护默认开启，放宽需要主动声明**。

超过上限时拒绝，错误码 `QT-BACKLOG-07`。被拒的任务不占 `pending`、不进队列。

## 7. 进程与身份边界

三个概念，**三个不同的东西**，不能用一个词串起来：

| 概念 | 实体 | 有节点身份吗 | 凭据 |
|---|---|---|---|
| **mesh** | `nexus-mesh` 进程 | ❌ **不是节点** | — |
| **webui** | `nexus-mesh-ui` 进程 | ❌ **不是节点** | 只读 ops 凭据 |
| **coordinator** | （已取消这个概念） | — | — |

### mesh 退出节点表

旧模型里 mesh 注册成节点 `coordinator`，实际只做两件没意义的事：
发任务（无生产调用方）、提供 `work.summary`（无生产调用方）。

**证据**：`app.py:167` 的 `_pulse_local_node()`，注释写着

> 协调节点是**本进程内的节点**，没有任何东西会给它发心跳 ——
> 于是启动 3 个心跳周期后它必然被判 stale。

这段 hack 的存在本身就是「mesh 不该是节点」的证明。退出后：
插曲删除、`local_node` 配置删除、观察窗上「协调中枢 ● alive」的假象消失。

### webui 是只读客户端，不是 observer

`nxs ui` 走 **ops HTTP 通道**，不是节点协议。这是对的，不要改：

- 它需要全量节点列表 + 指标 → 属于 ops 作用域
- 节点协议有意不提供全量映射

**⚠ 但「只读」目前是约定，不是强制。**

`nxs/ui/server.py` 的 docstring 写着「用**运维密钥**定期拉数据」，
而 `gateway.py:1090` 的 `approve` / `revoke` / `release` / `nodes` / `metrics`
**共用同一个 `_authenticate_ops()`**。

真实状态：**UI 进程里握着全网最高权限的密钥**，「只读」只是因为
UI 代码没去调 approve。

这与拆分 UI 的初衷（攻击隔离）正相反——它还要对外提供 HTTP 服务。

**必须加只读凭据**（成本很小）：

```
NXS_VIEW_SECRET   只能做 nodes / metrics
NXS_OPS_SECRET    全权，只留在 mesh 进程本机
```

`_authenticate_ops(required="view" | "ops")` 一个参数的事。
做完之后「UI 只读」是**可验证属性**，不是口头承诺。

### 风险隔离的边界（如实说明）

两进程分离能隔离的是：

| 攻击 | 影响范围 |
|---|---|
| webui 的 HTTP 端口被打 | `nexus-mesh-ui` 进程崩溃，看板失效，**网络运行不受影响** |
| webui 负载过高 | 同上 |
| **webui 进程被攻破** | ⚠ **取决于凭据**：加只读凭据 → 只能读；不加 → **可 approve/revoke，全网沦陷** |

第三行是加 `NXS_VIEW_SECRET` 的唯一理由。

## 8. 未实现与未来

### 多播（group）：现在不定义

交付模式枚举先只有 `unicast` 和 `broadcast`。
`multicast` 等 group 真做了再加枚举值 —— 否则又是一个
「枚举里有、但用不了」。

### `work.summary`：留着但没接线

全仓库查过：只在 `examples/node_run.py` 和一份配置里出现，
**没有任何生产代码调用它**。

它是「多节点协作需要汇总」的设想产物，但实际链路一直是单跳问答。
按 §5，广播结果**由调用方自己聚合**，所以它不是必需品。

**处置**：从 `coordinator` 的配置里移除（那个节点本来就不存在了）。
未来若出现「需要汇总者」的场景，它应由一个**真实节点**提供，
而不是 Mesh 内置。

### 设备/工具声明：自律项，只记录不强制

`tools` / `workdir` / `self_limits` 进 AgentCard，作用是：

| 作用 | 说明 |
|---|---|
| 审批时可见 | 运维批准前能看到「它要 Bash 权限」 |
| `nxs nodes` 可查 | 不用翻配置文件 |
| 变更记版本 | 但**不触发重批**（除非改 `role`/`domain`） |

**文档里必须写这一句**：

> ⚠ 工具与自限额是**节点自律**，不是强制。Mesh 无法阻止节点多用一个工具；
> 它能做的是让这件事**必须被声明、可被查看、变更留痕**。

### 错误码：27 → 23

**⚠ 一处需要修正的早期判断**

我最初写的是「`MX-RECEIVE-03` 并入 `MX-DOMAIN-02`」。**那是不对的** ——
这个错误码在代码里有 5 个调用点，覆盖**三种不同语义**：

| 调用点 | 真实语义 | 正确归宿 |
|---|---|---|
| `policy.py` 的接收白名单 | 域不可达 | `MX-DOMAIN-02` |
| `mailbox.py` / `registry.py` 未批准、不可路由 | **准入问题** | `AU-APPROVE-05`（新增） |
| `gateway.py` / `task.py` 任务不属于调用方 | **任务归属** | `LF-TASK-404`（已有，语义相同） |

第三项是白捡的简化：`gateway.py` 的原注释写「不存在与不属于自己返回同一个
错误，避免枚举」，而 `LF-TASK-404` 的定义正是「任务不存在，或调用方看不到它」
—— **本来就是一件事**。

一个错误码覆盖三种语义，排障时必须读代码才知道"这次的 RECEIVE-03 是谁不许谁"。

| 动作 | 错误码 |
|---|---|
| 删 | `QT-TASK-01` · `QT-BYTE-02` · `QT-BYTE-03` · `MX-DELEGATE-04` · `QT-CONC-05` |
| **拆分** | `MX-RECEIVE-03` → 按真实语义一分为三（见下） |
| 新增 | `QT-BACKLOG-07`（信箱深度）· `AU-APPROVE-05`（未批准） |
| 保留但**语义变更** | `MX-DOMAIN-02` → 纯可达性（不再兼管类型）<br>`WL-TYPE-404` → 类型未定义（不再是"没节点声明"）<br>`MX-ISSUER-01` → 判据简化为 role 可否发布 |
| 保留（Mesh 自保） | `QT-RATE-04` · `QT-CONN-06` |

### `UNIMPLEMENTED` 清单：7 项 → 归零

| 原清单项 | 新归宿 |
|---|---|
| `params_schema` 不校验 | ✅ **可以真正开始校验**——类型全局定义后，校验方与定义方是同一个 |
| `bytes_per_response` 不生效 | 配置项删除，配额归节点 |
| `bytes_per_day` 不生效 | 同上 |
| `roles.relay` | 字段消失 |
| `roles.observer` | 角色不定义 |
| `roles.executor` | 字段消失 |
| `roles.human_interface` | 字段消失 |

**归零的根源是归属清晰了。** 以前 `params_schema` 不生效，是因为
「每个节点各说一套 schema，谁也不知道该信哪份」。这是这轮设计
最实在的收益——**不是加功能，是把原来悬空的东西落地**。

## 10. 两个运维前提（写进文档，避免以后踩）

**① 角色数量少是前提**

删掉 `can_receive_from` 和 domain 的类型列表后，控制面变粗。
域隔离挡住了「跨域乱发」，但**同域内的 driver 现在是等价的**。

> 角色超过 5 个，或某个域内的 driver 超过 5 个，就该重新审视。

**② 角色粒度 = 能力边界粒度**

因为 Agent 不能声明「我只做角色能力的一部分」，所以
「只会查日历、不会查会议纪要的机器」**必须是一个新角色**。

这不是设计缺陷，是这套模型的必然代价：审批时一眼看清整体，
