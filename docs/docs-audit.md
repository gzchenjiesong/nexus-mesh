# 文档腐化审计（2026-10-26）

> 审计对象：全部 13 份文档（约 5300 行）与代码的一致性。
> 触发问题：**vibecoding 下，需求文档是真实的依赖与审核目标——文档腐化 = 依赖腐化。**

---

## 结论摘要

**有腐化，共 11 处，已全部修复。**

其中两处会导致**读者完全误判系统能力**：
`README.md` 的「尚未实现」表里列着**三个早已完成**的模块。
读者会以为要自己实现能力匹配、可观测、运维接口——实际三个都能用。

**根因不是疏忽，而是没有测试守护。** 项目自己的编号标准写着：

> ③ 能自动校验的才可信。靠人记住的规范必然腐烂——不是有人故意违规，
> 而是没人能一直记得。**每条规范都应有一条测试守护，否则它只是一段愿望。**

文档一致性此前正是一条"愿望"。现在有了 17 条守门测试
（`tests/test_docs_consistency.py`）与准则 C9。

## 三、一个反复出现的教训：**"零"要问清是累计还是增量**

这次审计里有个小插曲值得记下来。

我一开始决定"保留 README 的测试数 + 加守门测试"，理由是有守门就不怕腐化。
结果**每次往仓库加测试，README 就红一次**，得回去改一行。加了 3 轮之后
改主意了：这个数字**根本不该写在那里**。

判断依据是**变更频率**：

| 数字 | 变更频率 | 处理 |
|---|---|---|
| 测试总数 | 每次加测试 | **不写**（维护成本 > 信息价值） |
| 追溯项数 | 加功能点才变 | 写 + 守门 |
| demo 步数 | 极少变 | 写 + 守门 |

这不是"哪个更准"的问题，是**哪里的成本更高**的问题。
守门测试能保证准确，但它不能消除**维护动作本身**。

> 这个思路与 v0.8 修 `silent_stall` 时是同一条：
> 当时问的是"零产出是累计还是增量"，这次问的是"这个数字该不该存在"。
> 都是**先问清问题形态，再决定做法**。

## 四、审计方法（可复用）

脚本化优先，人工只做机器判不了的部分。

```
① 提取所有能用机器判定的事实
   ├─ 路径存在性（含相对路径的三种可能基准）
   ├─ CLI 命令（跑 --help 真探测，不靠正则猜）
   ├─ 端点（网关路由 vs 文档表格，双向）
   ├─ 错误码（errors.py vs 文档表格，双向）
   ├─ 数字（测试数、编号项、步数）
   └─ 模块状态（两个独立源的交叉比对）
② 人工判机器判不了的
   ├─ 描述的行为与代码是否一致（"空队列返回 204"要去看代码）
   ├─ 声称的能力是否实现（M14 那 5 项）
   └─ 指路牌指向的位置是否合理
③ 把能自动化的部分变成测试 ← 关键一步，否则下次重来
```

### 三个具体的坑（我自己踩过）

**① 审计脚本自己的误报比漏报更麻烦。**
第一版脚本把 `artifact-size.md`（相对 `docs/` 的路径）判成不存在，
把 `nxs verify`（真实存在）判成 CLI 不存在。**差点去"修"本来正确的东西。**
判断依据应该是"上下文是否已说明位置"，不是"路径能不能直接解析"。

**② grep 单一模式会误判。**
我一度以为协议文档说"空队列 204"是假的——因为 grep `send_json` 没找到。
实际代码用的是 `_send_status(204)`。**换个实现方式就漏了。**
必须看代码本身，不能只看 grep 结果。

**③ 审查自己的文档有盲区。**
这些文档都是我写的，我"记得"它们说了什么。所以必须先跑脚本，
再带着脚本的输出去读——而不是先读一遍然后觉得"应该没问题"。

## 五、现在还剩什么（诚实声明）

**已守住的**：能用机器判定的 17 类事实。

**守不住的**（只能靠人读）：
* 解释是否清楚（一段话能不能让新人看懂）
* 设计是否合理（选 A 不选 B 的理由是否站得住）
* 类比是否恰当
* 有没有遗漏的**应当说明**的东西

**下一批风险**：
* `docs/design/02-numbering-standard.md` 说"已迁移 147 处标识符"——
  这个数字没有守门，也没法验证（迁移是一次性动作，已无对照物）
* `deploy/README.md` 里的命令序列没有端到端测试
  （`nxs doctor` 有测试，但"照文档从零部署一遍"没有）

## 六、怎么复核这次审计

```bash
.venv/bin/python -m pytest tests/test_docs_consistency.py -q   # 17 条守门
```

想确认守门真的有效：随便把某个模块状态改错，或把 README 的步数改回去，
再跑一遍——它应该立刻报出文件与行号。
