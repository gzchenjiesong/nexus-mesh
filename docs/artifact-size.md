# 产物大小：实测与判断

> 这份文档回答一个具体问题：**产物到底能多大？我需要为此做什么？**
>
> 所有数字都是实测的，不是从配置值推出来的。测试方法见文末。

---

## 一、当前的真实上限

三层限制叠在一起，实际起作用的是**最外层的 HTTP body 上限**：

| 限制 | 配的位置 | 值 | 实际作用 |
|---|---|---|---|
| `max_body_bytes` | `server` | 256 KB | ✅ **真正的天花板** |
| 单次应答字节上限 | 节点 `self_limits` | 由节点自定 | ❌ **从未生效**（见下） |
| `MAX_FREETEXT_BYTES` | 代码常量 | 4 KB | 只作用于声明的自由文本字段 |

> ⚠ **单次应答字节上限是个死配置。** `check_quota(planned_bytes=...)`
> 这个参数在全部代码里**没有任何调用点**，所以它永远收到默认值 0。
> 换句话说：你把它配成 64 KB 或 64 MB，行为完全一样。
> 这是 v0.1 就登记在 `UNIMPLEMENTED` 里的遗留项，本文档顺带确认了它。

### 实测：文件塞进信封能到多大

产物以 base64 放进结构化字段（`kind=structured`）：

| 文件大小 | base64 后 | 完整信封 | 占 256 KB 上限 | 结果 |
|---|---|---|---|---|
| 1 KB | 1.3 KB | 1.9 KB | 0.8% | ✅ |
| 5 KB | 6.7 KB | 7.3 KB | 2.8% | ✅ |
| 10 KB | 13.3 KB | 13.9 KB | 5.4% | ✅ |
| 50 KB | 66.7 KB | 67.3 KB | 26% | ✅ |
| 100 KB | 133 KB | 134 KB | 52% | ✅ |
| **190 KB** | 253 KB | 254 KB | **97%** | ✅ 临界 |
| 200 KB | 267 KB | 267 KB | 104% | ❌ 超限 |
| 10 MB | 13.3 MB | 13.3 MB | 5200% | ❌ 差 50 倍 |

**结论：信封能带约 186 KB 的文件**（实测值；理论边界 190 KB 是
按纯算术推的，真实信封还有签名与元数据开销）。base64 固定膨胀 33%，
再加 JSON 信封的小额开销，整体约 1.34×。

## 二、那 10 MB 的文件怎么办

**不塞内容，传坐标。** 这条设计早就定好了：

> M9 产物通道：**默认走「引用传递」而非「内容传递」**：
> 信封里放坐标（如文件存储路径 / 本地存储相对路径 / 对象存储 key），
> 需要时再由消费方按自己的策略去取。

`kind="reference"` 就是为此预留的形态。实测：

```python
Artifact(level=Level.METADATA, kind="reference", data={
    "path": "/data/report-2026-10.pdf",
    "sha256": "9f2c...",
    "size": 10_485_760,
})
```

**10 MB 的文件，信封只占 96 字节。** 而且这条路**现在就能用**——
只要节点在自己的角色卡里声明了这些坐标字段：

```yaml
capabilities:
  - type: work.report
    level: metadata
    response_fields: [path, sha256, size, level]   # ← 坐标字段必须在白名单里
```

不需要新代码。字段白名单照常生效（这正是它该做的）。

## 三、所以 M9 该做什么（我的判断）

### 不需要做的：扩容

把 `max_body_bytes` 从 256 KB 调到 16 MB，技术上是一行配置。但**不该调**：

* 一个请求占 16 MB 内存，并发 64 就是 1 GB —— 那是给自己造 DoS 面
* base64 膨胀 33%，传 10 MB 文件实际跑 13.3 MB
* 更根本：把文件内容塞进消息信封，**违背设计文档自己定的"引用传递"原则**

### 真正缺的：坐标怎么被对方拿到

这是跨网络场景的**真实痛点**，也是我之前没说清的地方：

```
公司电脑（内网）        云端 coordinator
  /data/report.pdf  ←→  拿不到这个路径
```

`kind=reference` 传了坐标，但**对方可能根本访问不到那个位置**。
设计文档里说的「一次性令牌」和 `ArtifactStore` 都还没实现。

不过——**这个缺口是否需要补，取决于你的文件最终要落在哪**：

| 你的场景 | 该怎么做 | 需要写代码吗 |
|---|---|---|
| 文件留在公司电脑，coordinator 只要知道"有这个东西" | 传坐标即可，现在就能用 | 否 |
| 文件要真正搬到云端 | 需要共享存储（对象存储/S3）+ 上传下载 | 是，且要配密钥 |
| 两边都能访问同一台 NAS | 传相对路径，运维约定好挂载点 | 否 |
| 文件都小于 190 KB | 直接塞信封 | 否 |

## 四、给你的建议

按你说的"大部分几 KB、最大可能 10 MB"，我的判断是：

**先不做 M9，用现有能力跑起来。**

理由：

1. **几 KB 完全够用**——占上限不到 3%，连优化都不需要
2. **190 KB 以内的文件**（Word、Excel、小 PDF）直接塞信封就能传
3. **更大的文件**先用「传坐标 + 运维约定共享位置」过渡——
   比如两端都挂同一个 NAS，或节点把文件放到约定目录后把路径发出来
4. 真做对象存储集成，要引入凭据管理、生命周期、成本，
   **在你还没跑起来之前，这是过早优化**

如果实际跑起来发现"文件搬运"是高频需求，那时候再做 M9，
而且届时会更清楚该对接哪一种存储（S3？网盘？NAS？）。

> ⚠ 有一个**现在就该知道的限制**：`kind=reference` 目前只是
> "把坐标当普通字段传"，**系统不做任何校验**——不验证文件是否存在、
> 不验证 sha256、不保证对方能取到。
> 它是个约定，不是机制。用的时候要自己确认接收方能访问。

## 五、怎么自己复核

本文档的数字可以一条命令复现：

```bash
python examples/probe_artifact_size.py
```

它会打印三部分：信封开销换算、真实走 HTTP 的逐级探测、以及坐标形态的对比。

实测输出摘录：

```
② 真实走 HTTP，看在哪一层被拒
   ✓ 文件     1.0 KB → OK
   ✓ 文件    97.7 KB → OK
   ✓ 文件   185.5 KB → OK
   ✗ 文件   195.3 KB → FM-BODY-04      ← 在这里越界
   ✗ 文件   293.0 KB → FM-BODY-04

结论：信封能带约 186 KB 的文件。
```

判定依据：超过 `max_body_bytes` 时返回 `FM-BODY-04`。

## 附：这两个配置项的最终处置

⚠ **本节描述的是改造前的状态。权限模型改造后，这类"节点配额"配置项会被删除**
（见 [`design/06-agent-role-model.md`](design/06-agent-role-model.md) §6）。

理由：限额是节点自己的防御机制，Mesh 无法强制（命令在节点本机执行）。
节点正确的表达方式是自报 `self_limits`，额度用完时主动申报 `paused`。

真正的体积硬上限始终是 `server.max_body_bytes` —— 那个是 Mesh 自己的传输层限制，
一直都在生效。

## 附：为什么单次应答上限不生效是有道理的（暂时）

配额的设计意图是"限制单个节点的产出体积"。但**体积检查需要知道产物大小**，
而那要先把产物序列化——在边界校验**之前**序列化一次，
只是为了一次检查，成本不划算。

而且 `max_body_bytes` 已经在传输层挡了硬上限，
所以这个配额缺失的实际风险很小。这也是它一直没被优先补的原因。

同期登记的另一个未实现项是「按日字节累计」，风险类似。
两者都记在 `nxs/mgmt/config.py` 的 `UNIMPLEMENTED` 里，不会被静默遗忘。
